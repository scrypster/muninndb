# Hard invariants

Testable assertions a PR must never violate. Anchors are on `develop`. When an anchor's
line number drifts, the symbol name is the source of truth — re-locate by grep, don't
trust the number. If the live code disagrees with an assertion here, the code wins: flag
the stale invariant, don't enforce it.

Format: **[INV-n]** assertion — `file:anchor` — *why it matters / what breaks if violated.*

## Cognition invariants

- **[COG-1]** Unknown preset name falls back to `default`, never errors — `internal/auth/plasticity.go` `ResolvePlasticity`. *Config can never wedge the engine.*
- **[COG-2]** All plasticity overrides are clamped, never rejected (HopDepth 0–8, weights 0–1, ACTRDecay 0.01–2.0, HebScale 0–50, PASMax 0–10, **AssocHalfLifeDays 0.5–3650**) — `plasticity.go`. *Out-of-range config is impossible, not merely discouraged.* For `assoc_half_life_days`, `0` means **unset** (fall through to the preset), not "clamp to the minimum" — pinned by `TestResolvePlasticity_HalfLifeClamped`.
- **[COG-3]** The `working` preset equals `default` plus exactly `{RetentionDays:7, BehaviorMode:selective}` — pinned by `TestResolvePlasticity_WorkingEqualsDefaultPlusTwoDeltas` (`plasticity_test.go`). *Editing `default` must not silently drift `working`.*
- **[COG-4]** All presets share `RecallMode="balanced"`, `ArchiveThreshold=0.05`, `InlineEnrichment="caller_preferred"`, `EnrichmentEnabled=true`, `MaxEngrams=0`, `ScoringFusion=""` — `plasticity.go` preset table + the preset-invariant test suites. *These are cross-preset guarantees other code relies on.*
- **[COG-5]** The ACT-R content gate is `contentMatch = w.SemanticSimilarity*vectorScore + w.FullTextRelevance*normalizedFTS`, where `w` is the **resolved** weights (`resolvedWeights` — from the request/plasticity, falling back to `DefaultWeights{Semantic:0.35, FullText:0.25}` only when `req.Weights == nil`) — `internal/engine/activation/engine.go` `computeACTR` + `resolveWeights`. *The content gate is weight-driven, not a fixed constant. When no weights are supplied, the 0.35/0.25 defaults apply and unused components' budget is redistributed (the `1/0.65` scale). A change to `DefaultWeights` or to the resolve/redistribute logic reshapes scoring for every request that doesn't pass explicit weights — verify against the live `resolveWeights` before asserting what the effective weights are.* **Amendment (S1):** an explicit filter defines the candidate SET; the relevance threshold only RANKS within it. Two mechanisms enforce this for candidates that matched an explicit tag filter (`inTagPool`, verified by `passesMetaFilter`), both in `internal/engine/activation/engine.go`: (1) a content-match floor (`tagMatchFloor`) in `computeACTR` gives tag-only hits a sensible positive ordering below genuine content matches; (2) a **threshold bypass** at every Phase-6 scoring cut-site (RRF, CGDN, ACT-R, and legacy weighted-sum paths) — `if final < req.Threshold && !inTagPool` — so an explicit filter match is never dropped for scoring below the relevance threshold. The floor ALONE is insufficient: a floored, content-unrelated, decayed tag hit scores ≈`0.1 * softplus(B~0.17) ≈ 0.017`, below both the ACT-R default threshold (0.1) and the MCP surface default (0.5), so without the bypass every such candidate was still silently dropped. Before this, a content-unrelated tag hit produced `contentMatch = 0` under default (ACT-R) scoring, which zeroed `final` and dropped a candidate the caller explicitly asked for via `tags_all`/`tags_any`/`tag_prefix` — breaking `due:<=today` reminders whose content is unrelated to the query. See `computeACTR`, the four cut-sites in Phase-6 scoring, and `TestComputeACTR_TagPoolFloor_*` / `TestRawTagRange_SeedsDueItems_DefaultScoring` (which asserts 12/12 due items surface at BOTH production default thresholds). The bypass is safe at every site because each is guarded by `passesMetaFilter` first — only candidates that genuinely match the filter bypass the threshold. Non-tag candidates are still thresholded normally.
- **[COG-6]** The effective default threshold is mode-aware and decided in exactly one place per path, keyed on the **effective scoring mode**, not vault config: the `activateCore` coerce runs AFTER the weights block and tests `actReq.Weights.UseRRFFusion` — for rrf-scored requests it leaves `Threshold` at `0` ("unset") so `activation.Run()` applies rrf → 0.001 (#590); otherwise `activateCore` applies the fusion-matched default via `cog6DefaultThreshold` (0.1 for ACT-R, 0.5 for weighted_sum since #754). Keying on the effective scoring mode (rather than `resolved.ScoringFusion`) keeps the threshold default consistent with the scoring math that actually runs even when a caller passes explicit weights on an rrf vault (vault config says rrf, but caller-weights requests score ACT-R and must get the 0.1 default) — `internal/engine/engine.go` `activateCore`, `internal/engine/activation/engine.go` `Run`, `internal/mcp/handlers.go` `handleRecall`. An explicit caller threshold is never modified at any layer. Pinned at the **engine** layer (not `Run()`) by `TestActivate_RRFDefaultThreshold_EndToEnd` (`internal/engine/engine_rrf_threshold_test.go`) plus its ACT-R control `TestActivate_ACTRDefaultThreshold_Unaffected`. *R1 (#590 follow-up): before this, `activateCore` unconditionally coerced `Threshold==0 → 0.1` BEFORE `activation.Run()` ever saw the request, making #590's mode-aware default (rrf → 0.001) dead code on every production transport (MCP, REST, gRPC, MBP, embedded) — RRF vaults returned silently-empty default recall. The pre-existing `Run()`-level regression test (`TestRRF_ReturnsResultsWithDefaultThreshold`) stayed green throughout because it calls `Run()` directly with `Threshold: 0`, a call shape production never produces — exactly why the new pin lives at the engine layer instead.* MCP additionally: when the `threshold` arg is omitted, `handleRecall` consults the vault's `ScoringFusion` and passes `0` through (not its historical flat `0.5` prefill) for rrf vaults — and likewise passes `0` whenever a recall `mode` is present, because the mode's preset replaces the 0.5 default and resolving it is the engine's decision; an explicit caller-supplied threshold at or above 0.01 against an rrf vault that returns zero results gets a loud hint (never a silent, unexplained empty), not a clobbered value. **Amendment (#704):** recall-mode presets were a SECOND threshold decider that bypassed the mode-aware default — transports stamped ACT-R-calibrated preset thresholds (semantic 0.3, recent 0.2, deep 0.1) into the request, and the engine's vault-default `recall_mode` block overrode the leave-0-for-rrf decision, so a mode-carrying recall on an rrf vault was still silently empty. Now the ENGINE is the single preset decider: transports (MCP `handleRecall`, REST `handleActivate`) validate the mode name and forward it on the wire (`ActivateRequest.Mode` — previously silently dropped for raw MBP/embedded callers, now honored; gRPC's proto carries no mode field, so that surface is unchanged, and an invalid mode from a raw wire caller is silently ignored — fail-open on presentation, matching the engine's total-ignore of the wire field before; transports rejected invalid modes then and now). The engine resolves the preset in `recall_mode_preset.go` + the weights block, where the effective scoring mode is known: under rrf fusion the preset threshold ABSTAINS (Threshold stays 0 → `Run()`'s rrf floor); preset hops apply unless the caller set `MaxHops` or explicitly `DisableHops`. Preset WEIGHTS have three deliberate cases: (1) explicit weight-carrying mode (`semantic`/`recent`) with no caller weights → the preset defines the FULL weight vector from the ZERO base — the exact struct transports used to stamp — because the preset zero-value scheme cannot express semantic's implicit "decay/hebbian/access/recency = 0", and overlaying resolved defaults lets a fresh, recently-active engram score ~0.7 under legacy scoring with zero content match, above semantic's own 0.3 threshold (silently-wrong-results class, caught in this increment's refute); (2) caller weights present (any mode source) → preset fills only wire-zero fields, caller-set fields always win; (3) vault-default mode with no caller weights → the vault's resolved weights stand and only the `DisableACTR` strategy bit applies (a background default tints, it does not respecify scoring — byte-preserving develop's effective behavior on that path, where resolved-side zero-guards made the scalar fill a no-op). Presets never change the FUSION mode (`UseRRFFusion` comes from vault config or genuinely caller-explicit weights — previously, a weight-carrying preset stamped client-side silently flipped an rrf vault to weighted-sum scoring); on non-rrf vaults an explicit weight-carrying mode does select its scoring STRATEGY (the zero-base vector carries the preset's `DisableACTR` bit), exactly as its stamped form always did. `balanced` means engine defaults: the engine skips it, and MCP keeps its historical 0.5 surface default for it. Enforced, through `resolveScoringPlan` (the pure function `activateCore` uses), by `TestRecallModeCensus` (`internal/engine/recall_mode_census_test.go`: every preset × {wire, vault-default} × {actr, weighted_sum, rrf}, rules R1–R5, presets enumerated from `auth.RecallModeNames()`) and end to end by `TestActivate_RecentMode_EqualsDefault` (RED before: 10 rows vs 0). Structural rules pin numbers, so a preset can satisfy all of them and still admit nonsense (`{DisableACTR, Threshold 0.5}` as an ACT-R vault default returns 10 content-free rows at 0.70); the **behavioural census** `TestRecallModeCensus_ContentFreeAbstains` therefore runs a nonsense and a content-free query through `Activate` for every preset × {wire, vault-default} × {actr, weighted_sum} and requires abstention, with known violations allowlisted BY BEHAVIOUR (stale only when the cell actually abstains). `auth.ValidRecallMode` is derived from the preset map (`TestValidRecallMode_MatchesPresetMap`): a hand-written list let a map-only preset silently resolve to balanced on the vault path. **Allowlisted known violations, each failing the census if fixed without removing its entry:** F1 — `semantic` × {wire, vault-default} × {actr, weighted_sum} sets 0.3, below weighted_sum's 0.5 for the formula it forces (behaviourally REPRODUCED: an ACT-R vault whose default mode is semantic returns 10 nonsense rows at 0.70; as a wire mode semantic abstains); F2 — `deep` × {wire, vault-default} × weighted_sum sets 0.1 < 0.5. On a weighted_sum vault the alias inherits that vault default's pre-existing admission of content-free queries (~0.7 against its 0.5 bar, F4) — pinned as equality with a no-mode recall on that vault, not endorsed.
- **[COG-7]** ACT-R base-level is capped at ≈1.489 (ln(e^1.693−1)); Hebbian/transition boosts may exceed it, base-level alone may not — `activation/engine.go`. *"threshold=0.3 means the same thing in a fresh and a mature vault."* **Amendment (honest clock, increment 1):** the ACT-R base level used in recall is now IDENTICALLY `bLevelCap` for every engram: `softplus(B)/actrDenominator = 1`, so `Raw = ContentMatch` absent boosts and the gate's absolute score is `min(ContentMatch, 1) × Confidence`. `computeACTR` takes no age, access-count or cache-clock input for scoring — its signature carries no cache timestamp, so the hidden clock is unrepresentable there (principle #3), and it reports the APPLIED factors (`DecayFactor` = `Recency` = 1.0, `AccessFrequency` = 0). The `actr_decay` exponent is therefore inert under ACT-R; an explicit override, or a preset whose `d` differs from the default's (reference, knowledge-graph, scratchpad), WARNs once per vault per process (`Engine.warnInertACTRDecay`). A future earned-use advantage may raise the prior above neutral for RANKING only — the gate's `min(Raw, ContentMatch)` already keeps it from admitting a weaker match — and the prior may never fall below neutral (a below-neutral prior makes a once-read memory LESS findable than a never-read one). **Not guaranteed by this amendment: rank, which the in-memory Hebbian/PAS boosts can still move between recalls and across a restart (COG-34 residual). Accepted cost, stated plainly:** with age out of scoring, when two undeclared versions of a fact both match a query, the one phrased closer to the query ranks first even if it is older (the old cold behaviour returned only the newer one; the old fully-warm behaviour already ranked the closer-phrased one first). Exact score ties go to the newer (COG-34). A bounded per-vault salience term (age + earned use) is increment 2. weighted_sum and CGDN are NOT covered: they keep their additive recency/decay terms and the cache clock (residual D2 — they have no neutral value to pin to).   **Not top-level abstention**, which is what one round-7 evaluator literally asked for. #747/#754 is the hard-learned lesson in this exact area: suppressing BOTH sides destroys the true memory exactly as hard as the false one, and the agent that did the right thing loses both facts and the conflict itself. It also breaks the `Abstained` wire contract ("Empty iff Abstained is false") that two admission-worthy candidates do not satisfy. The complaint underneath the ask — "an agent commonly consumes only the first result, so this is confidently misleading" — is about presenting one side as THE ANSWER, not about returning the data; the demote, the always-on per-row annotation and the `conflict` block remove "the answer" while keeping both facts.

  **Named deviations from the design, each with its reason.** (a) **Ordering is by score, and only by score.** After the demote the whole response is RE-SORTED by score with a stable sort; adjacency is whatever that produces. Neither gather direction is used. The design asked for gather-to-highest, which would lift a cluster member above a strictly better unrelated row — exactly what demote-only forbids. The first implementation therefore gathered to the cluster's LOWEST-ranked member instead, and that is worse: on a corpus with a dominant conflicted row (0.859) whose declared partner is a weak straggler (0.018), it moved the best answer from rank 0 to rank 6, behind five rows it outscores by 2-8x, and returned a response that was no longer score-descending — an agent reading the first result then gets a 0.5 row presented as the answer over a 0.77 row, a worse lie than the one the phase exists to fix. Sorting by the demoted score is both demote-only AND monotone: near-tied rivals (the evaluators' shape) land adjacent for free, a dominant answer stays at rank 0 demoted and annotated, and nothing is ever lifted because a row's score only ever went down. The intra-cluster ladder (`sortContradictionCluster`) is applied first as a permutation within the cluster's own positions, so it decides sibling order on an exact score tie and nothing else. `keepAtLeast`/`adjacency_overflow` are computed from POST-SORT positions — the demote itself can push a member below rows that used to score under it, so computing against pre-sort ranks silently cuts a conflict in half while reporting that it did not (pinned by `TestContradictionHonesty_DominantAnswerStaysRankZero` and `TestContradictionHonesty_AdjacencyOverflowUsesPostSortRanks`). (b) The design's "if any cluster member survives the MaxResults cut, all of them do" does not hold at a tight limit: phase 6 truncates to `MaxResults` inside `activation.Run` BEFORE any post-pipeline phase, so a partner beyond the limit never reaches this phase, and injecting it is deferred (neither side is known to be right, so a conflict must never LIFT content into a result set it did not earn). What holds instead, and is pinned, is that the surviving row is still demoted and annotated with the partner named and `partner_in_results: false` — an agent consuming only the first result is still told it is disputed. The `keepAtLeast`/`adjacency_overflow` machinery still defends the case where a post-pipeline injector grows the set past `MaxResults`.

  **No absolute score ceiling.** An earlier draft carried a hard 0.95 cap and a `score_capped` wire field. Recall's `Score` is an absolute activation that is structurally an order of magnitude below that on every corpus measured, so the ceiling never once bound: it shipped a permanently-false flag on four surfaces and a test assertion that could not fail. Both were removed. The honest statement of the guarantee is the relative one — `contradictionDemote` (10%), a single `min()` against the row's own earned score.

  **The per-row annotation names exactly ONE partner, and the choice is total.** A row can be an endpoint of several declared edges; selection prefers a partner that is itself in the result set, then the lowest partner ULID. Taking the first edge encountered while ranging the map `GetAssociations` returns made both `with` and `partner_in_results` flip between identical queries against an unchanged vault (measured: a 33/7 split over 40 calls). Pinned by `TestContradictionHonesty_PartnerChoiceIsDeterministic`.

  **Fast path — three probes, cheapest first.** (1) A per-vault in-process flag set by `Engine.Link`, so a single-binary deployment honors a declaration on the very next query. (2) A bounded 0x0A seek (`PebbleStore.HasContradictionMarkers`, one iterator `First()`), the steady state and the only probe that sees an edge declared by ANOTHER process. (3) Once per vault per process, `DeclaredContradictions` — a bounded forward-association scan for declared-but-unflagged edges, its verdict memoised per vault.

  Probe 3 exists because 1 and 2 together had a PERMANENT hole. The in-process flag lives only in memory and the 0x0A marker is written only when the batch worker flushes, so a process that restarts between `muninn_link(contradicts)` and that flush loses the flag while the marker was never written — and nothing re-probed. Recall then silently stopped honoring a durable, correctly-declared contradiction FOREVER, which is the project's worst failure class dressed as a fast path. Pinned by `TestContradictionHonesty_SurvivesRestartBeforeTheMarkerFlush` (declare, assert no marker, clear the in-process state, recall must still honor) and `TestContradictionHonesty_ProbeIsPaidOncePerVault` (the memoisation, so recall never pays the scan twice). A probe ERROR — marker or declared-edge — degrades toward doing the work, never toward silently disabling the phase, and so does an incomplete scan (a vault with more forward associations than `DefaultDeclaredContradictionScanCap`).

  **Named residual:** an edge declared by another process/node AFTER this process memoised a clean verdict is honored only once its 0x0A marker lands (≤ one worker interval after the COG-23 #764 amendment) — probe 2 still runs on every query, so nothing regressed here.

  **`contradictionsDeclared` is never evicted, deliberately.** Eviction would have to prove no unresolved declared contradiction remains anywhere in the vault — a vault-wide scan, the exact cost this gate avoids — and getting it wrong turns honesty off silently. The entry is an empty struct keyed by an 8-byte prefix; the retained set is bounded by vault count. The false positive costs a read-only bounded phase that returns no block when nothing is live.

  Because the corpora contain no `contradicts` edge, the phase is a provable no-op on all three (`TestContradictionHonesty_NoContradictionsIsANoOp`), which is what keeps their numbers byte-identical. **Measured cost** (`BenchmarkRecallContradictionGate`, 200-engram synthetic vault, 1000 recalls x3): gate closed p50 348-383us / p99 1.03-1.32ms; gate OPEN p50 360-372us / p99 1.03-1.22ms — the open gate is inside the noise of the closed one. - **[STO-11]** **A prefix scan's exclusive upper bound comes from `keys.PrefixUpperBound`, never a naive last-byte increment.** Vault prefixes are 8 SipHash bytes, so roughly 1 vault name in 256 ends in `0xFF`, where `upper[len-1]++` wraps to `0x00` and produces an upper bound BELOW the lower bound: the iterator returns nothing, silently, forever, for that vault only. The forward side used to open-code a carry loop that stopped at index 1 — correct for the ~1-in-256 case STO-11 describes, but an ALL-0xFF workspace prefix (2^-64) ran the loop off the end and produced `0x03|00..00`, an inverted bound. Pinned by `TestGetRankingNeighbors_VaultPrefixEndingIn0xFF` (reverse), `TestGetAssociations_VaultPrefixEndingIn0xFF` and `TestGetAssociations_AllFFWorkspacePrefixIsNotSilentlyEmpty` (forward), and `TestAssocRangeEnds_NeverInvertTheirBound` (both, at the unit level). **The bound must also not be LOOSE (#816).** `PrefixUpperBound` used to increment the first sub-`0xFF` byte from the right and return WITHOUT clearing the trailing `0xFF` bytes, so `03 aa ff` yielded `03 ab ff` and admitted all of `03 ab 00 .. 03 ab fe` — a different prefix's keyspace, for ~1 prefix in 256. It now carries and TRUNCATES. `storage.PrefixIterator` open-coded a byte-identical copy of the loose loop and now delegates to the helper, so there is one implementation. **`PrefixUpperBound` returns `nil` — meaning UNBOUNDED, which is what `pebble.IterOptions.UpperBound == nil` does — when no finite bound exists (an all-`0xFF` prefix, or the empty prefix).** The values it used to return there (`append(prefix, 0x00)`, `[]byte{0x01}`) were bounds that EXCLUDED almost every key carrying the prefix, i.e. the silently-empty scan this invariant exists to prevent. Unreachable in-tree — byte 0 of every scanned prefix is an allocated type prefix (highest `0x45`) — but callers on destructive paths should know that `nil` widens. Pinned by `TestPrefixUpperBound_IsTightAndNeverCrossesIntoANeighbouringPrefix` (`internal/storage/keys/scan_test.go`), whose load-bearing half is "no key from a DIFFERENT prefix is admitted".

- **[STO-12]** **An association edge is refused unless BOTH of its endpoints have a live 0x01 engram record** — `internal/storage/assoc_endpoints.go` — the 0x03 forward key, the 0x04 reverse key, the 0x14 weight index and the 0x25 archive row all inherit this (#803).

  *A refusal at every writer, NOT an unrepresentable state, and the wording is deliberate.* The first version of this entry claimed an edge "may only exist while" both endpoints are live, which asserts the principle-#3 structural impossibility that the mechanism does not deliver. `engramExists` reads through `ps.db.Get` and the write commits a separate batch, with nothing spanning the two — `DeleteEngram` holds `casLocks.For(id)` across its read→commit (STO-2), the association writers take no lock — so a hard delete that lands inside the check→commit window still leaves a row. **Measured residual: 6 dangling rows per 400 forced `DeleteEngram`-vs-`WriteAssociation` races (pre-guard: 400/400).** Closing it structurally was considered and rejected: `casLocks` on both endpoints would work for `WriteAssociation` alone, but `pebbleStoreBatch` holds an open batch across arbitrary CALLER code between its check and its commit, so no lock discipline the store can enforce covers it — the claim would still have to be qualified, at the price of N-lock ordering against a single-lock `DeleteEngram`. The residual is a repairable row and it belongs to the deferred O(vault) integrity/repair pass, not to a lock.

  *Liveness is EXISTENCE, not lifecycle state.* `SoftDelete` `batch.Set`s the 0x01 key with `StateSoftDeleted`, and archiving is a state on a present record, so a soft-deleted or archived engram **is present** and its edges must survive — a state-aware predicate here would silently destroy every restorable engram's edges, which is worse than the leak it closes (pinned by `TestSTO12_SoftDeletedAndArchivedEndpointsKeepTheirEdges`). Only `DeleteEngram` removes 0x01.

  **Two layers, both required.**

  *(1) The cascades.* `DeleteEngram` cascades 0x25 in both directions (it scanned 0x03/0x04 only), and every hard-delete CALLER must clean the FTS and HNSW indexes, which live outside the store — `Engine.Forget(hard)` and **both** `Engine.PruneVault` arms (MaxEngrams and RetentionDays are separate delete loops with separate call sites) do so via `cleanSearchIndexesAfterHardDelete`. The 0x03/0x04 cascade scans must also obey **STO-11**: a 0x03 key is `prefix(25)|weightComplement(4)|dst(16)` and `keys.WeightComplement` is `MaxUint32 - uint32(w*MaxUint32)`, so `complement[0] == 0xFF` for every weight at or below ~1/256 and the complement is `0xFFFFFFFF` at weight 0 — which is byte-for-byte the position every PRE-FIX weight-1.0 edge was written at (`legacyFullWeightComplement`). The original naive `append(prefix, 0xFF)` bound sorted at or below all of those, so the cascade silently skipped them and nothing else ever reaped them. **Client-reachable at ordinary weights** (nothing clamps `Weight` on `Engine.Link` or the inline path), and it made `RepairLegacyFullWeightAssocKeys` a *creator*: that pass scans with a correct bound, so it saw the stranded legacy row the cascade missed and relocated it into a live, correctly-positioned dangling edge at startup. Both bounds now use `keys.PrefixUpperBound`, and the repair's `flushChunk` live re-validation additionally requires both endpoints — needed independently, because the vaults that pass exists for were hard-deleted by a pre-fix binary whose cascade could not reach the legacy position either. Note the other direction too: `keys.PrefixUpperBound` WAS LOOSE — it incremented the first sub-0xFF byte from the right and returned WITHOUT clearing the trailing 0xFF bytes, so for a 25-byte assoc prefix ending in 0xFF the bound spanned into the neighbouring engram's association keyspace; `storage.PrefixIterator` open-coded the identical loop. **#816 fixed both** (the helper carries and truncates; `PrefixIterator` delegates to it). **Every destructive scan bounded by a 25-byte `kind|ws(8)|id(16)` prefix nevertheless KEEPS its explicit `bytes.Equal(k[:25], prefix)` break** — belt and braces now rather than the sole protection, because a delete loop should not depend on a helper in another package for the only thing holding it inside its own keyspace, and because any future non-ULID id tail collapses the ~2^-64 gap below to zero. There are four of them: `DeleteEngram`'s 0x03 forward and 0x04 reverse cascades, `DeleteEngram`'s 0x25 archived-source cascade, and `reapArchivedEdgesFrom` (reachable from the recall read path via `RestoreArchivedEdges`). The 0x03/0x04 pair must additionally keep `SeekGE` rather than being converted to `PrefixIterator` (whose First/Valid shape changes the break-vs-continue semantics on short keys). **There is a FIFTH scan over the identical 25-byte `0x25|ws|src` prefix that has NO such break, so its upper bound is its ONLY protection**: `RestoreArchivedEdges`' own candidate loop, twenty lines above `reapArchivedEdgesFrom` in the same file. It hand-rolls its own TIGHT upper bound (incrementing from the right and zeroing every byte it wraps) instead of calling `PrefixUpperBound` or `PrefixIterator`, which is why it was correct while those were loose. #816 makes the shared helper agree with it, and **the loop still stays hand-rolled**: "equivalent today" plus "the only thing standing between this loop and fabricated edges" is not a combination to maintain at a distance. Dropping that bound — by consolidating onto the shared helper and then regressing it, or by "tidying" this loop for consistency with its neighbour — would make it FABRICATE a `victim → neighbour's dst` edge that never existed and stamp `restoredAt` on it, permanently exempting it from `GCArchivedEdges`; this loop is destructive AND creative, unlike the four above. Its `engramExists(ws, c.dst)` guard does not catch that: the dst read out of the neighbour's key is a real live engram, so liveness and the bound are orthogonal. The bound is pinned by `TestSTO11_RestoreArchivedEdgesCandidateScanStaysInsideItsOwnPrefix`; a prefix check must not be folded into that loop's existing `len(k) < 41 || len(v) < 26` skip, because `len(v) < 26` is value-shaped and must stay a `continue` while a prefix mismatch must `break`.

  *Read the ~1-in-256 number correctly.* It is the rate at which the BOUND IS LOOSE, not the rate at which anything is lost — the two differ by about 64 bits. To land inside the widened band a second engram must share the victim's first 14 ID bytes: the entire 48-bit ULID millisecond timestamp AND 8 of the 10 crypto-random entropy bytes, i.e. ~2⁻⁶⁴ *on top of* a same-millisecond collision. With ULID-shaped keys that is **not operationally reachable**, and every test of it constructs its IDs by hand. The guard is therefore **structural hygiene, not a live data-loss fix**: a mandated shared helper whose contract is wrong, compensated by an explicit per-key check at each call site, where any future non-ULID ID tail (a counter, a truncated hash, a content-addressed key) collapses the 64-bit gap to zero immediately — silently, on a delete path. Pinned by `TestSTO11_EveryDestructivePrefixScanStaysInsideItsOwnPrefix` (the table over all four scans; grow it when a fifth appears), `TestSTO12_DeleteEngramCascadeReachesEveryWeightPosition`, `TestSTO12_DeleteEngramCascadeStaysInsideItsOwnPrefix`, `TestSTO12_LegacyFullWeightRepairNeverCreatesADanglingEdge` and `TestSTO12_HardDeletePathsCleanTheSearchIndexes`.

  *(2) The guard.* **Enumerate the writer set from the KEY BUILDERS, never from method names or from prose** — `grep -e AssocFwdKey -e AssocRevKey -e AssocWeightIndexKey -e ArchiveAssocKey` over non-test Go. The first version of this entry enumerated by name, claimed four writers, and missed four more with no "Association" in their signature at all: the inline-`Associations` loops in `PebbleStore.WriteEngram`, `PebbleStore.WriteEngramBatch` and `pebbleStoreBatch.WriteEngram`, plus the singular `UpdateAssocWeight`. **Those three inline loops are client-reachable** — `mbp.WriteRequest.Associations` arrives from REST (`rest.WriteRequest` is a type alias), gRPC, MBP and the embedded library, so an ordinary client holding an ID across a delete landed three dangling rows with a nil error; only MCP escaped, because `muninn_link`/`muninn_remember` use `relationships`, which routes through the guarded primitive. The full creator set, all refusing with `ErrDanglingEndpoint`, is: `WriteAssociation` (the primitive, through which `autoassoc.processJob`, `NeighborWorker`, `GoalLinkWorker`, the refines writer, `plugin/store_adapter.go` and inline caller *relationships* reach the keyspace), `pebbleStoreBatch.WriteAssociation`, `UpdateAssocWeight`, `UpdateAssocWeightBatch`, `RestoreArchivedEdges`, and the three inline-`Associations` engram writers. Non-creators the same grep returns, and why they are exempt, are recorded at the head of `assoc_endpoints_writers_test.go`. Guarding one amplifier site would be cosmetic: the next worker added would reintroduce the class. Pinned by `TestSTO12_EveryAssociationCreatorRefusesDeadEndpoints` (the enumerated table; grow it when the grep grows) and `TestSTO12_InlineAssociationsCannotNameADeadEngram` (the surface-reachable arm, asserted against the same census as the delete paths).

  *The engram writers check the TARGET only.* The engram carrying the associations is their source and its own 0x01 key is Set in the same uncommitted batch, so a both-endpoints DB read would reject every engram that has ever carried an inline association. `WriteEngramBatch` additionally treats any caller-supplied id elsewhere in the same call as live, ORDER-INDEPENDENTLY, because it sees the whole slice up front — but that promise is only sound if the sibling actually commits: the per-item validations that run afterwards (encode, the up-front raw-tag validation, STO-12 itself) each `continue` without queueing that item's 0x01, so the referrer's edges to a refused sibling are `batch.Delete`d after the loop. **Not fixed by accumulating the sibling set incrementally** — that reintroduces the queue-order dependence `TestSTO12_BatchAssociationGuardIsQueueOrderDependent` documents for `pebbleStoreBatch` and refuses the legitimate referrer-first ordering. **The predicate for that post-loop delete is `engramExists` PLUS the set of ids that another item in the same call commits, never the batch outcome.** Two distinct ways a refused item is still a live endpoint, and the delete must survive both: (a) a refused *update* leaves its 0x01 record in place, which `engramExists` sees; (b) the SAME id appears twice in one call, once committing and once refused, which `engramExists` CANNOT see — the successful occurrence's 0x01 `Set` is still in the uncommitted batch, so a DB read returns false and the referrer's edges to an endpoint that is about to commit are deleted in the same batch, after the `Set` that made it live. Hence the `committedIDs` set alongside the existence check. In both cases deleting is unrecoverable loss, where the hole being closed only leaks a repairable dangling row. Note also that two later `continue`s in the same loop (`WriteRawTagIndexEntry`, the 0x22 last-access `batch.Set`) fire *after* the item's 0x01 and association Sets are queued; both are unreachable today (the first re-runs the identical validation, the second fails only past a 4 GB batch), but a validation moved below the queueing would invert the repair. Pinned by `TestSTO12_BatchSiblingThatFailsItsOwnValidationIsNotALiveEndpoint`. **`pebbleStoreBatch` must additionally treat an engram queued EARLIER IN THE SAME BATCH as live** — `RememberChild` and `Evolve` queue the engram and its edge into one uncommitted batch, so a DB-read-only guard would reject every atomic child-append and every evolve.

  **The guard FAILS OPEN on a read fault — but counts and logs it** (`GuardReadFaults`, plus a WARN rate-limited to one per 30 s because a corrupt block is a permanent key-scoped fault). Fail-open is right and is *not* in tension with #809: #809 refuses on a read failure because proceeding would fabricate metadata over live data; this permits because refusing would destroy a live edge that can never be recovered — opposite loss directions, one doctrine. A silent fail-open would not be: it reverts the whole invariant to pre-#803 behaviour with nothing in the logs.

  *Ancillary obligations.* `DeleteEngram` also drops the 2 s-TTL `assocCache` entry of every source that pointed at the victim: the ROWS all go, but the SERVED graph kept naming the dead engram until expiry. `RestoreArchivedEdges` REAPS an unrestorable 0x25 prefix rather than restoring it: a restore stamps `restoredAt`, and `GCArchivedEdges` requires `restoredAt == 0`, so a restored-then-re-archived dangling edge would be permanently GC-exempt (`reapArchivedEdgesFrom`, pinned by `TestSTO12_ArchivedEdgesFromAHardDeletedSourceAreReaped`). So the copy is paid by the seven writers instead of by every reader. *Mutating the returned struct in place is a data race against every concurrent recall AND publishes UNCOMMITTED state — the mutation is visible to readers the instant the assignment runs, before validation and long before the batch commits, which is how a rejected tag set reached `muninn_read` and filtered its own engram out of a recall (STO-18's history).* **A per-engram stripe lock is NOT a fix and four call sites documented that it was:** `casLocks` serialises writers against each other, and recall's readers never take it (`engram.go` says so at `UpdateTagsLocked`'s re-cache), so `SoftDelete`, `UpdateTagsLocked`, `UpdateConfidence` and `UpdateConfidenceWithContradiction` each raced a reader goroutine doing nothing but `GetEngram` in a loop — demonstrated under `-race` on the first and third before the fix. `cache.Delete`-before-`GetEngram` does not help either: `GetEngram` RE-CACHES what it decodes, so the pointer it hands back is shared again by the time the caller sees it. The seven fixed writers are `pebbleStoreBatch.mutateEngram` (#858's reported race, behind `SupersedeEngram`/`UpdateEngramState`), those four, `UpdateDigest` (the enrichment path — no lock at all, and it aliased the caller's `keyPoints` slice into the cached struct), and `Engine.Restore` (which mutated the cached struct purely to shape its return value, then returned the cache's own pointer). *#492 fixed this same class in dream dedup and guarded it with a doc comment on `L1Cache.Get`; that comment is accurate, is still there, and did not prevent any of these seven.* The guard is therefore mechanical: `TestCachedEngramMutationCensus` walks every non-test Go file in the module and fails on any field or element write through a `GetEngram`/`GetEngrams`/cache-`Get` value not released by `x = x.Clone()` earlier in the same function. Because its steady state is ZERO offenders, it cannot check itself — "found nothing" and "went blind" are the same green — so it carries the two checks `TestLastAccessElapsedCensus` had to grow: `TestCachedEngramCensusMatcher`, a fixture-driven unit test of the matcher (17 shapes, including `eng.Tags[0] =`, `eng.Field++`, the `for _, e := range engs` shape #492 came out of, and a clone of the WRONG engram not counting as a release), and `cachedEngramKnownSources`, a named floor of the seven functions the walk must still SEE binding a cache read. Behaviourally pinned by `TestReadModifyWriteWriters_DoNotMutateTheCachedPointer`, driven over the SAME `rmwWriters` table as STO-19-era `TestReadModifyWriteWriters_PerpetuateSentinel_DoNotHeal` so a new read-modify-write writer inherits the check, plus `TestMutateEngram_DoesNotMutateCachedPointer` and `TestMutateEngram_ConcurrentSupersedeSameID` (the #858 reproduction: RED reported three `WARNING: DATA RACE` at `batch.go` `oldState := eng.State` against `eng.State = StateSoftDeleted`). Stated residuals, all in the census doc: inter-FUNCTION taint is invisible, a bare `cp := *eng` is treated as safe (true for field writes, false for element writes), and a new slice-valued field on `Engram` that `Clone` forgets to copy is not detected by anything.

- **[STO-22]** **No read-through cache ever serves a value older than the last committed write to its key.** `internal/storage/cache_guard.go`, `cache_commit.go`, `snapshot.go`. The replication applier hands every committed repr to `InvalidateCommittedRepr` and drops all caches after a snapshot install. The L1 size counter equals the number of live entries (it moves only on absent→present `Swap` and present→absent delete). **Before:** a recall's snapshot read re-cached relevance 0.20 over a committed 0.90; a forgotten memory read as active and `Restore` refused it; a stale metaCache `oldState` made a restore skip its 0x0B move; one engram updated 60 times left count=58 with one live entry, so every stamped fill evicted a warm entry and every no-stamp fill was refused. **Not covered:** `recentActiveCache` (a 1 s TTL candidate-ID list that is re-read and filtered, by design never invalidated on write) and `vaultPrefixCache` (name→prefix, not engram state). **Not a cache property:** the write-write half (an unlocked writer losing a locked writer's update IN PEBBLE) is STO-24.
- **[STO-23]** **The retired set, recall's final filter and Read agree on liveness for every memory, always — and the source of truth is the 0x01 engram record.** `internal/storage/retired.go`, `clone.go`. - **[STO-24]** **Every read-modify-write of an engram record holds that engram's stripe lock (`casLocks.For(id)`, exported as `LockEngram`) from the read of the COMMITTED record to its commit, and writes back only the fields it owns.** `internal/storage/engram.go`, `entity.go` (`UpdateDigest`), `plugin_store.go` (`UpdateEmbedding`), `batch.go` (`mutateEngram`), `lease.go`. The read goes to Pebble (`Get`/`GetEngramUncached`), not to a value the caller read earlier: a struct read before the lock reverts whatever committed since, and STO-22 only promises the CACHE is not older than the last commit, not that the caller's copy is. Field-scoped writers patch the raw record (`patchMetaLocked` behind `UpdateMetadata`/`TouchAccess`/`AddAccessCount`/`CompareAndSet`; `UpdateRelevance`, `UpdateTrust`, `StampValidUntil`, `UpdateEmbedding`); whole-record writers (`SoftDelete`, `UpdateTags`, `UpdateConfidence*`, `UpdateDigest`) re-encode the fresh read. `StoreBatch.mutateEngram` (evolve's supersede, `UpdateEngramState`) only validates at queue time; the mutation is applied in `Commit` to the record as committed then, under every touched stripe taken in ascending stripe order (`stripedMutex.lockMany`, so two batches cannot deadlock). The lock is NOT reentrant: a caller that already holds it uses the `*Locked` variant (`UpdateTagsLocked`, `UpdateMetadataLocked`, `StampValidUntilLocked`, `SoftDeleteLocked`), and no code may hold one engram's stripe while calling a locked writer for another (stripes are shared, 256 of them). **Before:** a forget committing inside an unlocked writer's window came back active in 0x01/0x02 behind a soft-deleted 0x0B (the digest, the relevance patch, the EmbedDim patch); evolve's supersede reverted a trust change; a stamp reverted an access bump; two relevance writers orphaned a 0x10 bucket; dream dedup rewrote a representative's whole metadata from the start of the pass and resurrected it. A writer REPLICATES its batch before releasing the stripe, so the replication log holds same-engram batches in commit order (replicating after the unlock let a forget committed in the gap ship first, and a follower applied the older record on top — `TestReplication_SameEngramBatchesShipInCommitOrder`). The local WAL fsync is not held under a stripe: `UpdateEmbedding` and a `StoreBatch` with queued mutations commit NoSync, replicate, unlock, then sync the WAL (`syncWAL`) before returning; a sync failure is returned but the batch has already shipped (`TestUpdateEmbedding_SyncFailureStillReplicates`). ## Security & transport invariants

- **[SEC-1]** A `cap_` token must never set `IsAPIKey` — exactly one of `IsAPIKey`/`IsCapability` is set — `internal/mcp/context.go`, `internal/mcp/types.go`. *This is what makes the recursion guard structural.*
- **[SEC-2]** Any privileged MCP tool (one that mints/grants/creates) gates on `IsAPIKey && Mode==ModeFull && <opt-in env>` before dispatch — `internal/mcp/server.go` (`muninn_create_workflow_vault` is the template). *New privileged tools must copy this triple gate.*
- **[SEC-3]** `ValidateAPIKey` accepts only the `mk_` prefix; REST/gRPC/MBP call **only** `ValidateAPIKey`, never `ValidateCapability` — `internal/auth/keys_store.go`, `middleware.go`, `grpc/server.go`, `mbp/server.go`. *Keeps cap_ MCP-only, structurally.*
- **[SEC-4]** Capabilities carry a non-nil TTL at both mint (`GenerateCapability` rejects nil) and validate (nil/past expiry = expired) — `internal/auth/capability_store.go`. *No immortal credentials.*
- **[SEC-5]** Invalid `mk_`/`cap_` on MCP fails closed — never falls through to static-token or open-server auth — `internal/mcp/context.go`.
- **[SEC-6]** Every registered MCP tool is in exactly one of `mutatingTools`/`readOnlyTools`, and its bucket matches a per-tool decision a human recorded in `expectedToolClassification`; unknown tools blocked for observe AND write modes; unknown key modes rejected — `internal/mcp/context.go`, `server.go` (census in `internal/mcp/tool_classification_test.go`). *A tool with no classification silently escapes mode enforcement; a tool with the WRONG one hands an observe credential a write (#731). Coverage is not correctness — nothing yet derives a bucket from what the handler calls. Residual: the buckets are complementary, so a tool cannot be denied to observe AND write (#822). See the decision record.*
- **[SEC-7]** A vault-pinned credential rejects any differing `vault` argument and never echoes the pinned name — `internal/mcp/context.go` (also REST/gRPC/MBP). *No cross-vault action, no name leak.*
- **[SEC-8]** Unconfigured vaults are locked (fail-closed, `Public:false`) on REST/gRPC/MBP — `internal/auth/vault_config.go`.
- **[SEC-9]** Toolset filtering is **advertisement-only**; dispatch never consults it; unknown values fail **open to full** — `internal/mcp/toolset.go`. *Presentation preference, not a security boundary.*
- **[SEC-10]** SSE per-POST: both a cached `cap_` and a cached `mk_` session credential are re-validated (live key-store read) before dispatch, so a revoked or expired credential cannot keep dispatching on an open SSE session — `internal/mcp/server.go`. *The cap_ half closed the #612 confused-deputy; the mk_ half closed the symmetric gap in #617 (was #615). A PR touching the SSE POST path must not reopen either.*
- **[SEC-11]** Vault names are `[a-z0-9_-]{1,64}` everywhere via `IsValidVaultName` — `internal/auth/token.go`.
- **[SEC-12]** Static-token compares are constant-time with a length cap; keys/caps are looked up by SHA-256(secret) — raw secrets are never stored — `internal/auth/token.go`, `keys_store.go`, `capability_store.go`.
- **[SEC-13]** **In cluster mode, a client-originated write is accepted ONLY on the Cortex, and every mutation it makes is replicated.** Closed by #596/#631 claim 3 (was open, and was exactly those bugs). Enforced by one `WriteGate` function, installed by `cmd/muninn` only when cluster mode is enabled and wired to `ClusterCoordinator.IsLeader()`. It is held in FOUR places, deliberately: `Engine.refuseWrite`/`refuseNonLeaderWrite` (transport-agnostic backstop — the embedded Go library and any future transport inherit it), `auth.Store.refuseNonLeaderWrite` (vault config/plasticity, `mk_` keys, `cap_` tokens, admin records — which bypass `PebbleStore` entirely), and REST + MCP at the request boundary, which exist only so those two surfaces can answer with a precise status and the leader hint (REST 421 Misdirected Request + `X-Muninn-Cortex-Id`/`-Addr` + code 4015; MCP JSON-RPC -32002). gRPC maps the engine error to `FailedPrecondition` in a server interceptor; MBP frames it as error code 4015. REJECT, not forward — the argument (no node-to-node write RPC exists, forwarding amplifies split-brain, rejection adds no wait, and the join path already redirects this way) is recorded at `mbp.NotLeaderError`. **Completeness is census-derived, not a list**: `TestSingleWriter_RefusesEveryWriteOnFollower` runs `guardedOps` ∪ `additiveWriteOps` — the two write buckets `TestAppendMode_MethodCensus` (SEC-15) forces every exported `*Engine` method into — against a follower gate, and `TestSingleWriter_AdditiveCensusIsComplete` pins the additive half to `appendAdditive`. Configuration replication is the other half: `auth.Store.SetReplicator` puts every config/credential write into the same replication log as engrams (`internal/auth/cluster.go`), which it never entered before — a full join snapshot carried config because it iterates the whole DB, the incremental stream did not, so a failover served the pre-failover defaults. **Residuals, stated:** (a) the gate is evaluated once at the top of an operation, so a node demoted between the check and the commit still commits that one write — closing it needs `replication.ValidateFencingToken` to be called on the write path, and it has NO production caller today; (b) BACKGROUND workers that mutate replicated state on a follower (pruner, decay, archive GC) are NOT gated — they have no caller to mislead and `WipeForResnapshot` discards their output, but they are still divergence and remain open; (c) the REST route decoration is an explicit list, not method-based, because a method-based rule would also refuse `POST /api/admin/cluster/failover`, `/cluster/enable` and `/replication/promote` — the routes an operator needs ON a Lobe to recover from a lost Cortex. A write route missing from that list still cannot diverge (the engine/auth gates catch it); it just reports the refusal as a generic error instead of a 421.
- **[SEC-14]** The elevated trust level `verified` (human-confirmed / admin-certified) can only be set on a write by a caller whose ctx `auth.ContextMode` is `full` or `write` — an `observe` credential is rejected with `ErrInvalidRequest`, never silently downgraded — `internal/engine/engine.go` `resolveTrust`. The gate is enforced in the engine (`Write`/`WriteBatch`), so it is transport-agnostic *only if every transport populates `ContextMode`*: REST (`internal/auth/middleware.go`), gRPC (`grpc/server.go`), MBP (`mbp/server.go` HELLO, from the key's mode / full for open sessions), and MCP (`mcp/server.go` `dispatchToolCall`, full for authorized mode-less sessions) all do. A transport that reaches `Write` without setting `ContextMode` would *over-block* (reject a legitimate full write) — that was the S8 integration bug on MBP + default-config MCP; fixed and regression-tested (`mbp/trust_mode_test.go`, `mcp/trust_write_wiring_test.go`, `engine/trust_write_test.go`). **Recorded scope decision:** "write/full credential" (D4) is deliberately the bar — so an anonymous writer to a `Public` REST vault (mapped to `ModeFull` by design) and a `cap_`/`mk_` token minted with `full`/`write` mode *can* stamp `verified`. `verified` therefore asserts "written by a full/write-authorized principal," not "cryptographically human-attested"; a stricter human-only tier would need its own mechanism and is out of scope. *Every other trust level (`inferred` default, `external`, `untrusted`) is ungated. `source_type` is provenance-derived, never a write arg, so trust is the sole caller-settable discriminator — a write path that lets an observe credential stamp `verified` makes the anti-pollution capture tiering theater (S8/D4).*
- **[SEC-15]** An `append`-mode credential (`auth.ModeAppend`) may read and CREATE new engrams (`remember`/`remember_batch`/`remember_tree`/`add_child`) but is refused every operation that modifies or deletes an EXISTING engram/entity/lease/enrichment. Enforced at the ENGINE via `Engine.refuseWrite` — which calls `refuseNonLeaderWrite` (SEC-13) and then `refuseAppend` (returns `ErrAppendForbidden`) — on ALL 30 destructive methods (data-plane + vault-admin), so the guarantee is transport-agnostic — the MCP `isAdditiveTool` dispatch gate alone left REST/gRPC/MBP open (the #687 confirmed break; Restore/Link/PruneVault were later-found stragglers). `TestAppendMode_MethodCensus` reflects EVERY exported *Engine method and fails CI on any UNCLASSIFIED one, forcing each new method into guarded/additive/infra/read-only — real completeness, not a hand-maintained checklist (principle #6, cf. SEC-6). `TestAppendMode_RefusesEveryDestructiveOp` behaviorally proves all 30 guarded ops refuse append. *One recorded residual: the additive path may reinforce an existing engram's access metadata via content-hash-dedup `TouchAccess` (#682) — append strengthens, never overwrites/evolves/forgets/archives/re-trusts. This is the structural credential the flush write reflex uses so untrusted transcript content can never turn capture into destruction (cf. SEC-7 for the cross-vault half).* **Amendment (label pipeline, slice 2a):** `muninn_feedback` is additive (`additiveTools`), and `RecordFeedback`/`RecordFeedbackLabels` are in the census's additive bucket: append credentials may label. A label creates a new 0x29 child row and at most strengthens access metadata (the dedup-touch residual class); it never modifies or deletes a memory. Both refuse observe credentials in the engine (`ErrObserveForbidden`) as well as at dispatch. The response is uniform for a credential that cannot read the vault (`TestFeedback_WriteModeResponseUniform`), so a write-mode key learns nothing about existence; a credential that can read gets per-id outcomes, and only an unpinned one is told another vault's name (`TestFeedback_ReaderSeesOutcomesWriterDoesNot`, `TestFeedback_WrongVaultIsNamedToAnAllVaultReader`).

- **[SEC-16]** **A `ClusterCoordinator` is constructed only at boot, from the same configuration decision that wires `storage.PebbleStoreConfig.RepLogAppend`** — `cmd/muninn/server.go`. The store's replication hook is captured when `NewPebbleStore` runs and only when `cluster.yaml` already said `Enabled` at that moment; there is no setter for it afterwards, and adding one would not be enough (an in-flight write would race the install, and every write that landed before it would be absent from the log while the node presents a complete-looking replica to joiners). `POST /api/admin/cluster/enable` therefore persists the configuration and answers **`202 Accepted` with `restart_required: true`** rather than starting anything — a coordinator built mid-process reports itself enabled, accepts Lobes, ships them a snapshot, and replicates none of the node's subsequent writes; it also never receives `SetMOL`, so it never prunes. That was #628, and it is why the runtime factory seam was **deleted** rather than completed: the bad state is now unrepresentable, not merely discouraged (principle #3). *Reintroducing any path that builds a coordinator outside boot reopens it.* Pinned by `TestClusterEnable_RequiresRestartAndBuildsNoCoordinator` and `TestEnableClusterRuntime_NeverStartsACoordinator` (`internal/transport/rest/`). Note the pre-enablement history is covered by the join-time snapshot, not by the log: `JoinHandler.HandleJoinRequest` sets `NeedsSnapshot` for every joiner and quotes `SnapshotSeq = repLog.CurrentSeq()`, and the snapshot is a full Pebble snapshot — so a replica that joins after a restart-enabled node comes up is complete even though the log starts empty.

- **[SEC-17]** **A bulk transfer's liveness bound is progress-based, never a fixed deadline on the whole transfer** — `internal/replication/peer_conn.go` (`progressWriter`). A single constant applied to a variable-size frame is a threshold measured against one quantity and applied to another: the frame may be a 40-byte heartbeat or a 1 MB snapshot chunk, and the link may be loopback or a WAN tunnel. The pre-#627 5 s per-frame deadline made replica catch-up **self-reinforcing** — a replica applying more slowly than the primary pushed filled the socket buffer, one write crossed 5 s, the stream died, and it rejoined further behind. The write deadline now renews on every byte the peer accepts, so "slow" and "wedged" are different conditions, and **raising the constant is not an acceptable substitute for this shape**. Three bounds keep it finite and must all stay: `sendIdleTimeout` (no bytes accepted at all ⇒ dead), `sendMaxDuration` (a dribbling peer may not hold one connection's write slot forever), and `sendSlotWait` (a caller that cannot get the write slot gets `ErrPeerBusy` — **the peer is alive, the connection must NOT be torn down**, so the shared MSP broadcast tick never blocks behind a multi-megabyte transfer and the streamer retries rather than dying). *A `Send` error path that treats `ErrPeerBusy` as a connection failure re-creates the spiral from the other end.* Pinned by `TestPeerConn_Send_SurvivesSlowButProgressingPeer`, `TestPeerConn_Send_WedgedPeerStillFails`, `TestPeerConn_Send_OuterBoundStopsDribblingPeer`, `TestPeerConn_ControlSendDoesNotBlockBehindBulkWrite`. Related: a restarted stream resumes from the highest position the primary can prove the replica holds (`ClusterCoordinator.streamStartSeq` — last ack, or the join-time `SnapshotSeq`, whichever is higher), never from 0; resuming from 0 made the re-transfer volume track the log size instead of the lag.
- **[SEC-18]** **The session signing secret is never blank.** `auth.Bootstrap` (`internal/auth/bootstrap.go` `loadOrCreateSessionSecret`) returns a non-blank secret or an error: a missing `auth_secret` is generated; a blank one (`isBlankSecret`: empty, or only NUL and ASCII-whitespace bytes) is replaced with a WARN; one that exists but cannot be read is an error, never overwritten. The file is written temp-then-rename (`writeFileAtomic`) so a write that fails part-way leaves the previous file or none. `cmd/muninn/server.go` refuses to start on an empty secret, and `NewSessionToken` / `validateSessionToken` (`internal/auth/session.go`) neither issue nor accept a token under one — anyone can compute an HMAC under an empty key. Why it matters: `rest.withAdminMiddleware` and the UI server skip admin auth when the secret is empty (a test convenience), `VaultAuthWithAdminBypass` grants full mode to any cookie that validates, and a whitespace-only or zero-filled file is a key anyone can guess. Pinned by `TestBootstrap_BlankSecretFileIsReplaced`, `TestBootstrap_UnreadableSecretIsNotReplaced`, `TestWriteFileAtomic_FailedWriteLeavesTargetUntouched`, `TestAdminAPIMiddleware_EmptySecretAcceptsNoToken`, `TestVaultAuthWithAdminBypass_EmptySecretGrantsNoBypass`, `TestSessionToken_EmptySecret`. Residuals: a non-blank secret is honored at any length (an operator may have provisioned it), so a short or low-entropy hand-written secret is weak but not refused; the empty-secret branch in the two servers still exists for tests; when a blank `auth_secret` is a symlink, the link itself is replaced by a regular file; a crash between creating and renaming the temporary file leaves a `.auth_secret-*` file that nothing removes.
- **[SEC-19]** **Over gRPC, a `write`-mode (ingest-only) credential is refused every RPC that returns stored memory or vault state — Read, Activate, Stat, ListVaults, Subscribe and AdjustConfidence — and an `observe` credential every RPC that mutates.** `internal/transport/grpc/server.go`: `denyWriteOnlyRead` on those six; `denyReadOnlyMutation` on Write, BatchWrite, Forget, BatchForget, Link and AdjustConfidence. AdjustConfidence carries both: it changes an engram and returns the resulting confidence, and with `delta` 0 it changes nothing, so for an ingest-only key it is a read. A refusal is `PermissionDenied` and the engine is never called. This is the gRPC counterpart of REST's `auth.WriteOnlyGuard`/`ReadOnlyGuard` and of the MCP tool buckets (SEC-6). Every RPC in the service descriptor carries a class (handshake, read, mutation, or mutation-and-read) in `rpcClasses`, pinned by `TestEveryRPCHasAModeClass`, so an RPC cannot be added without deciding which modes may call it; `TestCredentialModeMatrix` checks every mode against every RPC through the real auth interceptors. Before this, none of the six had a write-mode check. Residuals: (1) Link, Write and Forget answer differently for an id that exists and one that does not, as their REST equivalents do for a write-mode key. (2) The guards are per-handler calls, so a new handler still has to call the right one (the matrix fails if it does not). (3) `append` is not restricted at the transport; its limits are the engine's (SEC-15).
- **[SEC-20]** **Over MBP, the credential's mode is enforced at dispatch, on every frame: an `observe` credential is refused every frame that mutates (WRITE, LINK, FORGET) and a `write`-mode (ingest-only) credential every frame that reads (READ, ACTIVATE, STAT, SUBSCRIBE, UNSUB).** `internal/transport/mbp/frame_modes.go`: `frameRoutes` holds, for each frame type the client listener serves after HELLO, its class (control, read, mutate, or mutate-and-read) beside its handler, and `dispatchFrame` (`mbp/server.go`) calls `admit` before the payload is decompressed or decoded. A refusal is the protocol's auth-failure frame — `ErrAuthFailed` (4010) with the message REST and gRPC give, "read-only key cannot write" / "write-only key cannot read" — the engine is never called, and the answer is the same whether or not the request is well formed or its target exists. That order is itself pinned, because nothing else noticed when it was reversed (moving `admit` behind decompression left every other test in the package green): `TestDispatch_ARefusedFrameIsNeverDecompressed` and, over real TCP, `TestRefusedFrameIsNotDecompressedOverTheWire` send frame types the session may not send with the compressed flag set — once with garbage, once with a valid payload that decodes to 8 MiB — and require the refusal itself, not a decompression error, and no allocation for the payload (SEC-21 rests on the same order). It is one choke point rather than a call in each handler (cf. SEC-19 residual 2), and it fails closed three ways: a frame type with no route is served to no one; a route whose class was left at its zero value is served to no one, a full key included, so a new opcode cannot be routed without deciding its class; and a mode the server does not recognize, or a connection carrying none, is refused every frame (as MCP does, SEC-6). The mode is the one HELLO stored on the connection — the key's own, or `full` for a credential-less session on a `Public` vault, which is full access by design on every transport — and HELLO is not served twice on a connection, so the mode cannot change under it; it is checked on each frame because dispatch is the one place every frame passes. MBP has no server-to-client stream today (ACTIVATE answers in one frame, and a subscription registered over MBP has no delivery function), so there is no later message that escapes the check; a streaming response added later must be reached only through a routed frame. Each class is the one the same operation has on REST (`ReadOnlyGuard`/`WriteOnlyGuard`), gRPC (SEC-19) and MCP (SEC-6); UNSUB exists only here and takes SUBSCRIBE's class. (This line used to justify that by saying only a credential that may read can hold a subscription, which was more than the code enforced: UNSUB then removed whatever subscription had the id it was given, on any vault, whoever held it. What is true since SEC-26 is narrower and is enforced: UNSUB reaches only a subscription made on the same connection, and a connection that may not SUBSCRIBE has made none.) The cluster opcodes (0x20–0x41) share MBP's framing but are not routed by this listener at all: they are served by the cluster listener (`cmd/muninn` `handleClusterConn`) behind its own join/peer-hello handshake, and this gate neither sees nor affects them. Pinned by `TestEveryDispatchedFrameHasAModeClass` (the route table against a decision table recorded in the test, in both directions), `TestCredentialModeMatrix` (full / write / append / observe / no-key-on-a-public-vault against every frame type, over a real TCP connection to a real engine and auth store), `TestUnroutedFrameTypesReachNothing` (every unrouted opcode, the cluster range included, is answered with an error and reaches nothing), and `TestModeRefusal_TruthTable` / `TestAdmit_*` for the gate itself — all in `internal/transport/mbp/`. Before this, HELLO stored the mode on the connection and nothing read it: an observe key could store a memory, rewrite one through an upsert, link two (including as contradicting) and soft- or hard-delete one, and an ingest-only key could read a memory by id, run recall, read vault statistics and open or close subscriptions. Residuals: (1) `append` is not restricted at the transport; its limits are the engine's (SEC-15), and the matrix shows them holding over MBP — a WRITE is a create or, with `upsert_mode`, a rewrite, which only the engine can tell apart. (2) As on REST and gRPC (SEC-19 residual 1), WRITE, LINK and FORGET answer differently for an id that exists and one that does not, for a write-mode key. (3) The class test pins the route table, not `dispatchFrame`'s control flow: a special case written into the dispatcher itself is caught by the matrix alone.
- **[SEC-21]** **A compressed MBP frame decodes to at most what an uncompressed frame may carry (`MaxPayloadSize`, 16 MiB); the bound holds WHILE decoding, so refusing a payload costs memory in proportion to the limit and never to what the payload claims or expands to; and what a connection's frames decode to is charged to that connection.** `internal/transport/mbp/compress.go` (`decompressBounded`, `requireOneFrame`), `decode_budget.go` (`decodeCharged`, `connDecodeBudget`). The decoder is never left to choose a buffer. A frame whose header declares its decoded size is refused before anything is allocated when that is over the limit, and otherwise decoded into one buffer of exactly that size. A frame that declares nothing (a streamed frame; also what a one-shot encoder emits below 256 bytes) is decoded into a pooled 384 KiB scratch buffer and copied out at its own size; only a frame that FILLED the scratch buffer gets a buffer that holds the limit, once — a frame that is bad rather than big stops at the scratch buffer. The payload must be exactly one zstd frame: `requireOneFrame` finds the frame's end by walking its block headers, decoding nothing, and refuses trailing frames, stray bytes and skippable frames, because every concatenated frame costs the decoder a fixed setup of a few kilobytes whatever it holds (2,000 hundred-byte frames cost 8 MiB to decode 200 KB, and a 16 MB payload holds over a million). Per connection, at most 32 MiB of decoded payload is in flight — decoded and not yet handled; a frame that does not fit is ANSWERED at once with `ErrRateLimited` (4012), never held (`decode_budget.go`: `decodeBudget.tryCharge` is a compare-and-swap on a counter; nothing in the budget blocks). **Nothing waits for the budget, and a frame never holds part of it while asking for more** — `frameCharge.hold(n)` gives back what the frame holds and then takes `n` in one step. The first version of the budget waited, and a streamed frame held its scratch-buffer charge while it waited for the limit-sized one: one burst of 64 such frames (212 bytes each, PINGs on a keyless connection) left 61 of them holding the whole budget in small charges with none able to take the large one — every frame of the connection hung, the reader behind them never returned, and the connection and its goroutines were not released even after the client had gone. With no waiting there is nothing to deadlock. The budget is per connection, not shared: one shared budget would cap the server's total but would let any single connection, an unauthenticated one included, have everyone else's compressed frames refused by keeping it full; per connection, a connection can only get its own frames refused, and the total is bounded only by the number of connections (residual 1). **What the zstd library's limits bound was measured, not read off their names** (klauspost/compress v1.20.2): `WithDecoderMaxMemory` refuses a DECLARED size before allocating, but for an undeclared one only compares the output after each block while `DecodeAll` appends and reallocates — about six times the limit before it refuses (97 MiB for a 16 MiB limit) — and it silently caps the frame's window at the same figure, so it cannot be set low for a cheap first attempt; `WithDecodeAllCapLimit` makes the buffer the bound, but reports an undeclared overrun with an untyped error and after the buffer has been outgrown once. Hence both options, and every buffer chosen here. Pinned in `internal/transport/mbp/`: `TestDecompressPayload_RefusesPastTheFrameLimitWithoutAllocatingIt` (asserts on `runtime.MemStats.TotalAlloc`: 0 MiB to refuse a declared 24 MiB, 17.5 MiB to refuse an undeclared 40 MiB; fixtures are tens of MiB so the test is safe on unfixed code), `_FrameLimitIsTheUncompressedLimit`, `_OneFrameOnly`, `_RoundTrips` (every frame shape still decodes; a small frame costs a small allocation; a corrupt one costs nothing), `TestDecodeBudget_*` (refused at once, not held; nothing stays charged on any of thirteen ways a frame can end — `inUse` and the server-wide total are back at zero after each; 128 frames at once all come back; connections do not share a budget), and over real TCP `TestCompressedBombOverTheWire` (one compressed PING on a session with no credential), `TestEveryFrameOfABurstIsAnswered` (the 64-frame burst: every frame answered — 3 of 64 before), `TestConnectionDecodeBudgetOverTheWire` (the frame that does not fit is answered 4012 while the first is still being handled; a second connection is unaffected; a client gone mid-request leaves nothing charged) and `TestNothingStaysChargedAfterABurst`. Before this, `DecompressPayload` called `DecodeAll(data, nil)` and compared the result with 100 MiB afterwards: a 5 KB frame declaring 24 MiB was decoded in full and accepted, the library allocates whatever a header declares up to its own 64 GiB default, and PING — open to every session, including one with no key on a public vault — was enough to deliver it. Residuals: (1) this bounds what COMPRESSION adds. An uncompressed frame may still be 16 MB, a connection runs 64 frames at once, and connections are not counted: the server has no overall budget for request payloads. (2) A streamed frame between the scratch size and the limit, or one that goes bad late in the scratch buffer, costs one limit-sized buffer. (3) A frame declaring a window over 16 MiB is refused (only `--ultra`/`--long` encoders emit one); a client that concatenated frames or sent more than 16 MiB decoded must change. (4) The other decompressors in the tree are not reachable by an API client and were left alone: `storage/erf` decodes stored record content with no bound (its input is the server's own encoding of content capped at 16 KB, unless raw records arrive by replication, admin import or restore); vault import streams gzip but allocates each key and value by its declared length (admin session only); self-upgrade extracts a checksum-verified release.
- **[SEC-22]** **An MBP connection closes its outgoing channel only after every handler it started has returned.** `internal/transport/mbp/server.go`: `readerLoop` spawns one goroutine per frame and, before it returns, takes every slot of the per-connection semaphore — which is waiting for every handler, since each holds a slot until it returns; `handleConnection` closes `writeCh` only after that. The handlers answer with a non-blocking send on `writeCh` (`queueFrame`, `queueErrorFrame`), and a send on a closed channel panics whether or not it is in a `select` with a `default`; the handler goroutines have no `recover`, so that panic ends the process — every vault and every transport with it. Before this, `handleConnection` closed `writeCh` the moment the reader saw the socket close, so any client that disconnected with a request still being handled (a WRITE or an ACTIVATE outlasts the round trip) crashed the server, and a session needs no credential on a `Public` vault. It needed no intent either: a client that timed out or was killed mid-request did the same. The handlers are deliberately NOT cancelled when the client goes: what was asked for before the disconnect is carried out, and the answers nobody reads are dropped by the writer. Pinned by `TestClientGoneWithRequestsInFlight` (`internal/transport/mbp/teardown_test.go`): three WRITEs held in the engine, the keyless client closes, the handlers are released — on the old code the test binary dies with `panic: send on closed channel` (and the race detector reports the send/close race first); after, a new connection is served and all three writes reached the engine. *Anything that makes a connection end early — a refused credential, a server-initiated close — goes through the same teardown and relies on this.* Residual: a handler that never returns keeps its connection's goroutines alive; nothing bounds how long a handler may run.
- **[SEC-27]** **Before HELLO succeeds, an MBP connection is on one fixed clock and may make the server hold almost nothing.** (Numbered after the invariants below it; it sits here because it belongs with the connection-lifecycle invariant above.) `internal/transport/mbp/server.go` `handleConnection`: `helloTimeout` and `maxHelloPayload`. From accept until HELLO_OK has been written the socket carries ONE deadline, 15 seconds, for reads and writes together — not a deadline per read, so a peer that sends a byte now and then does not keep the connection — and it is cleared once the session exists, after which a client may hold the connection idle. The value is the REST server's `ReadTimeout`, the in-tree bound on the same thing (the time a client has to deliver a request); like that one it is a constant, not a setting. The HELLO frame is read with `readFrameLimited(conn, maxHelloPayload)`: a header that declares more than 64 KiB is refused on the header alone, before the payload is allocated or awaited (a HELLO is a version, a 46-byte key, a vault name of at most 64 bytes, a client name and a few capability names). On a TLS listener the TLS handshake happens inside the same clock, on the first read. Before this there was no deadline and no size limit other than the frame's: a peer with no credential could hold a goroutine and a file descriptor for as long as it kept the socket open by sending nothing, and sixteen bytes — a header declaring a 16 MiB HELLO — made the server allocate 16 MiB for it and wait. Pinned over real TCP by `TestHandshakeHasADeadline` (a connection that sends nothing, one that sends half a header or half a payload, one that dribbles a byte at a time inside the deadline, forty silent connections after which the goroutine count is back at its baseline, and a HELLO that arrives inside the deadline followed by an idle period three deadlines long and a PING that is still answered) and `TestHelloPayloadIsBounded` (closed in under a millisecond with nothing allocated; 16.7 MiB allocated and still waiting before). Residuals: (1) **there is no idle timeout after the handshake, deliberately** — whether any client keeps a connection idle between requests without sending PING has to be established first, since dropping a pooled connection would be a regression. (2) A frame being read after the handshake is still allocated at its declared size, up to 16 MiB, before its payload arrives, and the reader waits for it without a deadline.
- **[SEC-28]** **The MBP listener holds a bounded number of connections, counted from accept.** `internal/transport/mbp/connection_cap.go`; `acceptLoop` in `server.go`. A connection takes a place the moment it is accepted — before HELLO, since the cap is what bounds the connections nobody has authenticated — and gives it back when `handleConnection` returns. One past the cap is refused, and **refusing costs the accept loop nothing whatever the peer does**: `refuseAtCap` does no I/O with the peer and never waits — it hands the connection, without blocking, to one of two refusal workers (a queue of sixteen), or closes it outright when they are busy. A worker puts everything it does with the peer under ONE 500 ms deadline, reads and writes both, answers `ErrRateLimited` (4012, "server is at its connection limit") so a legitimate client sees why, and closes. The first version wrote that answer from the accept loop under a write deadline only. The listener can be TLS (`cmd/muninn` passes `--tls-cert`/`--tls-key` through and `ServeListener` wraps the listener), and on TLS the first write runs the TLS handshake, which reads from the peer; a write deadline does not bound a read, so one peer that connected at the cap and sent nothing stopped the listener accepting anyone (`TestRefusingAtTheCapNeverHoldsUpAccept`: with eight silent peers at the cap on a TLS listener, no connection was admitted within 5 s of a place coming free; now 5 ms). Refusals are logged at WARN at most once per 10 seconds with the number refused since the last line. **The default is derived, not picked.** The tree had no listener-level connection limit to follow (the nearest things are gRPC's `MaxConcurrentStreams(500)` per connection and REST's request-rate limits), so it comes from what a connection can make the server hold, measured against a real server with 400 connections: about 5 KiB accepted-but-silent, about 21 KiB and two goroutines established-and-idle, and **16 MiB for a connection that has sent a 16-byte frame header declaring a 16 MiB payload and then nothing**, because the payload buffer is allocated at its declared size when the header is read. That last figure sets the default: the cap is the number of such connections that fit in a quarter of the process's memory limit (`debug.SetMemoryLimit(-1)`, which `cmd/muninn` sets from `MUNINN_MEM_LIMIT_GB`) — 1 GiB / 16 MiB = 64 at the default 4 GiB, 256 at 16 GiB, never below 16, and 64 when the process has no memory limit. `MUNINN_MBP_MAX_CONNECTIONS` overrides it, in the manner of the REST rate-limit variables (read by the transport, documented in the server's usage text and the generated env file); a value that is not a positive integer is refused with a WARN and the default is used, never read as "no limit". The cap in force is in the `mbp: listening` log line. Pinned over real TCP by `TestConnectionCap` (the connection past the cap is refused with an answer and closed; a burst of 60 gets none through and the established connections still answer; 61 refusals produce one warning; closing a connection frees its place; and connections that have not said HELLO hold places until the handshake deadline of SEC-27 clears them) and by `TestDerivedMaxConnections` / `TestResolveMaxConnections_Override`. Before this the listener accepted connections without limit. Residuals: (0) **the cap turns exhaustion into lock-out, it does not prevent it: one source can occupy every place.** A peer that can open sessions — with no key at all when any vault is `Public`, as `default` is out of the box — can hold all of them, and legitimate clients are then refused at this listener while the process and the other transports stay up. Three mitigations were evaluated and none was built. *A per-source-address cap below the global one* cannot be given a default that is both useful and harmless: every client of the default deployment has the source address 127.0.0.1, and a server in a container sees every host client through a published port as one address (measured: four separate host clients all arrived as 172.17.0.1, the bridge gateway), as does one behind a proxy or a NAT, so in the common topologies "per source" is "everyone" and the only safe default is the global cap itself; an attacker with several addresses is not bound by it at all. *The handshake deadline* (SEC-27) does return the places of peers that never say HELLO, after 15 seconds, but a peer that reconnects takes them again, and a peer that does say HELLO is not on a clock. *An idle timeout for sessions with no key* would clear out abandoned ones, but a PING is enough to stay busy, so it does not stop a deliberate squatter. What would is not letting unauthenticated peers reach the port. (1) the cap bounds how many connections can each hold a frame's worth, not how much one connection holds: a connection may have 64 frames in flight at 16 MiB each if it actually sends them, and nothing budgets request payloads across the server. (2) The 16 MiB-for-16-bytes allocation the default is derived from is itself avoidable — the buffer could grow with what arrives — and removing it would justify a much larger default. (3) A deployment with more concurrent MBP clients than the default must set the override; the default is conservative on purpose and the changelog says so.
- **[SEC-23]** **An MBP connection, and a push stream on REST or gRPC, is authorised for as long as what authorised it holds, checked on every frame and before every push — not once, when it opens.** `internal/transport/mbp/vault_scope.go` `sessionEnded`, called at the top of `dispatchFrame` before the frame is looked at in any other way; `internal/auth/keys_store.go` `APIKeyStillValid`. A keyed session ends when its key would no longer validate: its record is gone (revoked), it has expired, or the record under the same secret is no longer the vault and mode the session was opened as (nothing changes a key in place today; if something ever does, the session does not carry on as what it used to be). A session with no key ends when the vault it was opened on is no longer `Public`. A frame sent after that — of any type, routed or not, whatever its payload — is answered `ErrAuthFailed` (4010), "api key is no longer valid" or the vault's "requires an API key", the engine is not reached, and the connection is closed: `vaultScope.end` stops the reader with a read deadline, the frames already being handled finish and are answered (SEC-22), and the socket closes. Frames ADMITTED before the revocation are carried out; the check is at admission. Because it sits in front of `admit` (SEC-20) and of decompression (SEC-21), an ended session learns nothing else from what it sends — not "unknown message type", not a mode refusal, not a decompression error. **Validity is read from the auth store on every frame, deliberately, and not cached**: the store is the only thing every change to a key goes through. On a cluster follower a revocation arrives as a replicated batch applied straight to storage and never passes through `Store.RevokeAPIKey`, so a cache invalidated there would stay valid on exactly the nodes that serve reads. The cost was measured: `BenchmarkAPIKeyStillValid` 2.0-2.1 µs, 424 B and 11 allocations per frame for a keyed session (one point lookup and one JSON decode, 1,000 keys in the store); `BenchmarkGetVaultConfig` 0.8-1.0 µs and 7 allocations for a keyless one. Against a loopback round trip (`BenchmarkRoundTrip_*`, 100-350 µs on a loaded machine) that is inside the noise; the allocations per round trip went from 19 to 30 (keyed PING), 19 to 26 (keyless PING) and 46 to 57 (keyed READ). Pinned in `internal/transport/mbp/revocation_test.go` over real TCP against a real engine and auth store: `TestRevokedKeyStopsWorkingOnAnOpenConnection` (full / write / append / observe keys × every operation of the mode matrix, each key revoked between the handshake and the frame), `TestExpiredKeyStopsWorkingOnAnOpenConnection`, `TestLockedVaultEndsAKeylessSession` (every operation, PING and UNSUB included, which name no vault and were never checked against one), `TestEndedSessionIsToldNothingElse`, `TestRevokingOneKeyLeavesOtherConnectionsAlone`; and `TestAPIKeyStillValid` in `internal/auth`. Before this the key was looked at once: after `RevokeAPIKey`, or past its expiry, an open connection still read, wrote and hard-deleted for as long as it stayed open (59 cells of those tests fail on the previous commit). This is the MBP counterpart of SEC-10, which re-validates an MCP session's credential on every POST. **Amendment (push streams):** the same holds for the two streams that push memory content for as long as they stay open, REST `GET /api/subscribe` (SSE; `rest/server.go` `handleSubscribe`) and the gRPC `Subscribe` stream (`grpc/server.go`). Both ask `auth.Store.StreamStillAuthorized` (`internal/auth/stream_auth.go`) BEFORE EVERY PUSH and, with nothing to push, every 30 seconds (the SSE keepalive tick; `subscribeRecheckInterval` on gRPC, which had no tick of its own), and end the stream when the answer is no: an SSE `error` event, or `Unauthenticated`, saying "api key is no longer valid" or that the vault "requires an API key". Ending the stream ends its subscription, so a revoked key stops occupying one of the vault's subscription places within 30 seconds whether or not anything is written. The check is the one read described above, per push: `BenchmarkStreamStillAuthorized` 2.7-4.0 µs, 424 B and 11 allocations keyed, 1.1-1.9 µs, 272 B and 7 allocations with no key (measured on a loaded machine), against a push that is rate limited to 10 a second per subscription by default and costs a JSON or protobuf encode and a flush. A push already written to the socket when the key is revoked has been delivered; the check is before the write. Pinned over real HTTP and real gRPC against a real engine with its trigger system running: `TestPushStreamEndsWhenItsAuthorisationDoes` (`internal/transport/rest/subscribe_revocation_test.go`) and `TestSubscribeStreamEndsWhenItsAuthorisationDoes` (`internal/transport/grpc/subscribe_revocation_test.go`), each covering a revoked key, an expired key, a keyless stream whose vault is locked, an idle revoked stream that only the tick can notice, and a second stream that must be left alone; and `TestStreamStillAuthorized` in `internal/auth`. Before the amendment every one of those streams went on delivering: over SSE a push carrying content arrived after the revocation while the same key was answered 401 on `/api/stats`. Present in every tag from v0.1.0 to v0.11.0 (the route, the key check at open and the delivery loop were read at each). **What remains, not fixed here:** a stream opened under an admin session cookie is not ended when the cookie's 24 hours run out. Session tokens are stateless and nothing revokes one, so there is no revocation to honour, but the stream outlives the token. That covers `GET /api/subscribe` with a session cookie and the console's own `/events` and `/api/admin/cluster/events` streams. gRPC unary RPCs and REST requests validate the key on every call. Deleting or renaming a vault does not touch its keys.
- **[SEC-24]** **Statistics are about the caller's one vault. Only a verified admin session gets figures that cover the server.** `internal/engine/engine.go` `Stat` (`statVault` / `statServer`), `mbp.StatRequest.ServerWide`, `auth.AdminSessionFromContext`. The scoping is in the ENGINE, so it holds on every transport and for a transport that forgets to filter: MBP STAT, REST `GET /api/stats`, gRPC `Stat` and MCP `muninn_status`/`muninn_guide` all hand `Stat` the vault their caller is entitled to, and the answer is about that vault only — `engram_count` is its count, `vault_count` is 1, `coherence` has at most its own entry, `storage_bytes` is 0 (the store's on-disk size is one figure for every vault, so reporting it tells a single-vault caller how much everyone else holds), and `scope` says `vault` so a reader knows those are not the server's figures. The server-wide answer (every vault's coherence entry by name with its engram total, the vault count, the on-disk size; `scope: server`) has to be asked for with `ServerWide`, and **`ServerWide` has no wire name** (`msgpack:"-" json:"-"`): no frame and no JSON body can set it, so no client can ask — only server code at a call site that has established who is asking. (2) The six SDKs read only fields that are still sent (`engram_count`, `vault_count`, `index_size`, `storage_bytes`, `coherence`); none surfaces `scope` yet. (3) `engram_count` reads one higher than the number of engrams written on a fresh vault (3 for 2, while the coherence entry says 2); that predates this change and was left alone.

Only a verified admin session is told every vault on the server.** `auth.VaultsVisibleTo` (`internal/auth/middleware.go`); REST `handleListVaults` (`GET /api/vaults`); gRPC `ListVaults`. Pinned by `TestVaultsVisibleTo` (`internal/auth`), `TestVaultListScopeMatrix` (REST over a real listener and engine with three vaults: no key on a public vault, observe / full / append keys, a write key refused, no key on a locked vault refused, the admin session listing all, a forged session cookie treated as none), `TestListVaultsScope` (gRPC) and `TestVaultList_*` / `TestListVaultNamesAdmin_SendsTheSession` (`cmd/muninn`, against a stand-in server that scopes the way the real one does). Before this, REST returned every vault's name to a caller with no credential on a public vault — the `default` vault is public out of the box, so to anyone who could reach the port — and to any pinned key; and gRPC returned every name to any key, while its own comment said anonymous callers are refused "to prevent cross-vault name enumeration". Residuals: (1) a key holder is told its own vault's name here, as it already is by MBP's HELLO answer and MCP's `muninn_status`. (2) A REST server built with no auth store at all authenticates nothing on any route and lists everything; `cmd/muninn` never builds one. (3) The six SDKs' list-vaults calls return one name when used with a key. (4) Names of public vaults are not listed to a caller with no key either: a public vault needs no key, so its name is what stands between it and anyone who can reach the server, and it is only as hard to find as it is to guess.
- **[SEC-26]** **A subscription's id is chosen by the server, and over MBP a subscription belongs to the connection that made it: only that connection can end it, it counts against that connection, and it ends when the connection does.** Engine: `SubscribeWithDeliver` (`internal/engine/engine.go`) always assigns a fresh random id and ignores `SubscribeRequest.SubscriptionID`, because ids are ONE namespace across every vault (`trigger.SubscriptionRegistry.byID`), so an id a client could choose is an id it could choose to be somebody else's; and `SubscriptionRegistry.Add` refuses an id that is already registered (`ErrSubscriptionIDTaken`) instead of replacing the entry, so the bad state cannot be built by a future caller either. MBP: `vaultScope.subs` (`internal/transport/mbp/vault_scope.go`). SUBSCRIBE takes one of the connection's `maxSubscriptionsPerConnection` (8) places and records the id it was given; UNSUB ends a subscription only if its id is in the connection's own set, and any other id — another connection's, another vault's, one that does not exist — is left alone and answered exactly as an id nobody holds has always been answered (UNSUB_OK), so the answer says nothing about whether it exists; when the connection ends, after its handlers have returned (SEC-22), every subscription it still holds is removed. REST's SSE stream and gRPC's `Subscribe` stream already removed their one subscription when the stream ended and never let a client address a subscription by id; gRPC did pass a client-chosen id through to the registry, which the engine change closes. Pinned by `TestSubscriptionsBelongToTheirConnection` (`internal/transport/mbp`, real TCP and a real engine, asserting on what is REGISTERED, not on what a client was told): a connection ends its own subscription; UNSUB does nothing to another connection's in the same vault, nor to one in another vault, and is answered as for an id nobody holds; a chosen id is not used and two vaults' subscriptions never share one; three subscriptions are gone when their connection closes; 150 SUBSCRIBEs on one connection are granted 8 and another subscriber can still use the vault; and full / append / observe / keyless sessions may subscribe and unsubscribe while a write key may not. Also `TestRegistry_AnIDIsRegisteredOnce` / `TestTriggerSystem_SubscribeRefusesATakenID` (`internal/engine/trigger`) and the UNSUB row of the mode matrix, which now ends a subscription its own connection made. Before this, measured on the previous commit: any connection's UNSUB removed whatever subscription had the id it named, in any vault; a client-chosen id replaced another vault's subscription of the same id in the registry, after which the victim's own unsubscribe removed the attacker's entry and left the victim's listed for its vault with nothing able to remove it; a subscription outlived its connection; and one connection was granted 97 of a vault's 100 subscriptions, after which nobody else could subscribe to it. Residuals: (1) **a subscription made over MBP still never delivers a push.** The engine registers it with no delivery function and this server never writes an ACTIVATION frame, so over this transport a subscription is a place in the vault's limit and nothing else; it is now bounded and cleaned up, but SUBSCRIBE over MBP is accepted and does not work. (2) The limit is per connection, not per credential: one key with thirteen MBP connections, one gRPC connection with a hundred concurrent `Subscribe` streams (the server allows 500 streams on a connection), or a hundred SSE requests can still take all 100 of a vault's subscriptions. A per-credential limit was considered and not built, because a backend that serves many end users' SSE streams with one key would run into it. (3) REST SSE and gRPC push streams are authorised when they open and not again (SEC-23). (4) A client that sent `subscription_id` is answered with a different `sub_id`.
