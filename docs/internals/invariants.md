# Hard invariants

Testable assertions a PR must never violate. Anchors are on `develop`. When an anchor's
line number drifts, the symbol name is the source of truth — re-locate by grep, don't
trust the number. If the live code disagrees with an assertion here, the code wins: flag
the stale invariant, don't enforce it.

Format: **[INV-n]** assertion — `file:anchor` — *why it matters / what breaks if violated.*

---

## Cognition invariants

- **[COG-1]** Unknown preset name falls back to `default`, never errors — `internal/auth/plasticity.go` `ResolvePlasticity`. *Config can never wedge the engine.*
- **[COG-2]** All plasticity overrides are clamped, never rejected (HopDepth 0–8, weights 0–1, ACTRDecay 0.01–2.0, HebScale 0–50, PASMax 0–10) — `plasticity.go`. *Out-of-range config is impossible, not merely discouraged.*
- **[COG-3]** The `working` preset equals `default` plus exactly `{RetentionDays:7, BehaviorMode:selective}` — pinned by `TestResolvePlasticity_WorkingEqualsDefaultPlusTwoDeltas` (`plasticity_test.go`). *Editing `default` must not silently drift `working`.*
- **[COG-4]** All presets share `RecallMode="balanced"`, `ArchiveThreshold=0.05`, `InlineEnrichment="caller_preferred"`, `EnrichmentEnabled=true`, `MaxEngrams=0`, `ScoringFusion=""` — `plasticity.go` preset table + the preset-invariant test suites. *These are cross-preset guarantees other code relies on.*
- **[COG-5]** The ACT-R content gate is `contentMatch = w.SemanticSimilarity*vectorScore + w.FullTextRelevance*normalizedFTS`, where `w` is the **resolved** weights (`resolvedWeights` — from the request/plasticity, falling back to `DefaultWeights{Semantic:0.35, FullText:0.25}` only when `req.Weights == nil`) — `internal/engine/activation/engine.go` `computeACTR` + `resolveWeights`. *The content gate is weight-driven, not a fixed constant. When no weights are supplied, the 0.35/0.25 defaults apply and unused components' budget is redistributed (the `1/0.65` scale). A change to `DefaultWeights` or to the resolve/redistribute logic reshapes scoring for every request that doesn't pass explicit weights — verify against the live `resolveWeights` before asserting what the effective weights are.* **Amendment (S1):** an explicit filter defines the candidate SET; the relevance threshold only RANKS within it. Two mechanisms enforce this for candidates that matched an explicit tag filter (`inTagPool`, verified by `passesMetaFilter`), both in `internal/engine/activation/engine.go`: (1) a content-match floor (`tagMatchFloor`) in `computeACTR` gives tag-only hits a sensible positive ordering below genuine content matches; (2) a **threshold bypass** at every Phase-6 scoring cut-site (RRF, CGDN, ACT-R, and legacy weighted-sum paths) — `if final < req.Threshold && !inTagPool` — so an explicit filter match is never dropped for scoring below the relevance threshold. The floor ALONE is insufficient: a floored, content-unrelated, decayed tag hit scores ≈`0.1 * softplus(B~0.17) ≈ 0.017`, below both the ACT-R default threshold (0.05) and the MCP surface default (0.5), so without the bypass every such candidate was still silently dropped. Before this, a content-unrelated tag hit produced `contentMatch = 0` under default (ACT-R) scoring, which zeroed `final` and dropped a candidate the caller explicitly asked for via `tags_all`/`tags_any`/`tag_prefix` — breaking `due:<=today` reminders whose content is unrelated to the query. See `computeACTR`, the four cut-sites in Phase-6 scoring, and `TestComputeACTR_TagPoolFloor_*` / `TestRawTagRange_SeedsDueItems_DefaultScoring` (which asserts 12/12 due items surface at BOTH production default thresholds). The bypass is safe at every site because each is guarded by `passesMetaFilter` first — only candidates that genuinely match the filter bypass the threshold. Non-tag candidates are still thresholded normally.
- **[COG-6]** RRF mode forces threshold to 0.001 when the caller threshold ≥ 0.01 — `activation/engine.go` (RRF scores live in [0,0.05]). *Preserves #590's fix: an explicit caller threshold under RRF is respected, not clobbered.*
- **[COG-7]** ACT-R base-level is capped at ≈1.489 (ln(e^1.693−1)); Hebbian/transition boosts may exceed it, base-level alone may not — `activation/engine.go`. *"threshold=0.3 means the same thing in a fresh and a mature vault."*
- **[COG-8]** In RRF mode, BFS-traversed candidates must carry a non-zero rrfScore or they vanish from results — `activation/engine.go`. *Traversal reachability must not silently drop.*
- **[COG-9]** Soft-deleted/archived engrams are always filtered in phase-6 scoring and in entity boost — `activation/engine.go`, `engine_entity_boost.go`. *HNSW has no delete; the filter is the only guard.* **Amendment (valid-time, planned relaxation):** under `as_of=T` the design admits soft-deleted engrams that carry an explicit validity window covering T (evolve-superseded predecessors are stamped for exactly this) — records soft-deleted by plain `muninn_forget` (no stamp) stay hidden even from `as_of`; deletion still means deletion. **The relaxation is NOT yet implemented** (deferred from valid-time increment 1): today `as_of` filters only among currently-visible engrams, so evolve predecessors are not yet resurrected by time-travel. A PR implementing it must confine the relaxed filter to the `as_of` path.
- **[COG-10]** Co-activation (recall-time Hebbian) never updates confidence — only user feedback and contradictions do — `engine.go`. *"Evidence of relevance, not evidence of truth."* **Amendment (importance):** Importance is likewise never moved by access or co-activation — only the caller sets it (write/evolve; evolve inherits the predecessor's explicit value unless overridden). `TouchAccess` still moves only AccessCount/LastAccess — never Confidence, Trust, Stability, or Importance (a Stability write-on-read was designed and then deferred: Stability feeds the weighted_sum/RRF DecayFactor score component, so it would change recall results in those modes — see the TouchAccess doc contract). The three axes stay structurally distinct: Confidence = truth, Importance = priority, AccessCount = use. The use-time `EffectiveImportance` derivation (`internal/storage/importance.go`) is never written to storage — stored 0 always means "unset".
- **[COG-11]** Observe mode (`ReadOnly`) skips activation-log, Hebbian, and PAS writes — `engine.go`, `activation/engine.go`. *A read must not mutate learning state.* (Known wound: archive-restore in phase-4.75 still writes even for observe — see soft spots.)
- **[COG-12]** `Recall`/`Activate` never bumps engram AccessCount — `engine.go`. *Recall is not an access for decay purposes.* **Amendment (S2/#682):** AccessCount is bumped (via `store.TouchAccess`) by exactly these channels — explicit `RecordAccess`; content-dedup reinforcement on `Write`/`WriteBatch` (1/day cap); `RecordFeedback(useful=true)`; and **`Engine.Read` by id** when the read is not read-only and the vault's `ReinforceOnRead` plasticity is enabled (default true). The read channel is what finally makes decay/importance learn from use (RecordAccess was dead before). The invariant's core still holds: the multi-result `Recall`/`Activate` path never bumps — reads that reinforce are single-engram, caller-intended fetches, and observe-mode/`read_only:true` reads suppress it (COG-11, S3). A change that makes `Activate` reinforce, or that drops the read-only/observe suppression, violates this.
- **[COG-13]** Idempotency check precedes content-hash dedup on the write path — `engine.go`. *Re-submitting a known op_id with drifted content returns the original, deliberately.*
- **[COG-14]** Caller-supplied embedding ⇒ `DigestEmbed` flag set + inline HNSW insert; the retroactive embedder must never overwrite it — `engine.go`. *Don't re-embed what the caller already embedded.*
- **[COG-15]** The pruner only ever **hard-deletes**, and runs only for vaults with `MaxEngrams>0` or `RetentionDays>0` — `engine.go` PruneVault / runPruneWorker. *Soft-delete would leave relevance-index entries → infinite prune loop.* **Amendment (importance):** the MaxEngrams path skips candidates with `EffectiveImportance >= storage.HighImportanceFloor` (0.7) — see COG-20 — and when those exemptions leave `pruned < excess` it logs a **WARN** and stops (degrade loudly, no loop; a vault marking most memories high-importance cannot shrink via this path — documented residual, protected-fraction cap is the increment-2 lever). If candidate metadata cannot be loaded, the MaxEngrams pass is skipped for the cycle with a WARN rather than deleting importance-blind.
- **[COG-16]** Association decay requires `HebbianEnabled && AssocDecayFactor>0` — `engine.go`. *Decay of learned edges is gated on learning being on.*
- **[COG-17]** Hebbian weight updates are log-space multiplicative, capped at 1.0, seeded at 0.01 — `internal/cognitive/hebbian.go`. *Prevents overflow and runaway weights.*
- **[COG-18]** Entity boost is rarity-weighted, capped, and contract-gated: each shared entity contributes `0.15 × idf` (idf vault-local-n / store-global-df, so ubiquitous entities contribute ~0), credited once per target regardless of seed count; total boost per engram is capped at 0.30 (low end of the BFS weight range — saturated entity evidence may tie the weakest genuine edge, never a mid-strength one); seeds are the TopN=5 results that themselves cleared the threshold (a tag-bypass admission must not seed); injections must clear the caller's threshold and the rest of phase 6's result contract — meta filters, `ExcludeUntrusted`, lease visibility (#548), and the COG-19 valid-time gate; results are re-truncated to MaxResults after boosting — `engine_entity_boost.go`, `engine.go` (tightened in #581, reworked in #570). *Ubiquitous entities must not flood recall, and the boost path must honor the same result contract as phase 6 (#569, #654).*
- **[COG-19]** Invalidation is always a `ValidUntil` stamp, never a delete; default recall never returns an engram whose `ValidUntil <= now` — the single shared predicate is `storage.Engram.ValidAt`/`IsExpired` + `activation.PassesValidity`, enforced in phase-6 (`activation/engine.go`, beside `passesMetaFilter`) AND at the final post-entity-boost gate (`engine.go` `activateCore`), pinned by `TestCOG19_Pin` (`internal/engine/valid_time_test.go`). Stamp surfaces: `Evolve` (batch `SupersedeEngram` — soft-delete + stamp, atomically), explicit `RelSupersedes` links (skip-if-closed), `muninn_forget.not_true_since` (overwrite), `muninn_restore` (clears). *Validity is a HARD filter; cognition ranks only survivors. A new recall-adjacent surface (entity_state, where_left_off, brief, find_by_entity) that returns engrams without this predicate can lead with an expired fact — the "May figure" bug — so gate coverage is a per-surface adoption obligation (increment 2). The default gate excludes only EXPIRED facts, never future-`ValidFrom` ones.*

- **[COG-20]** An engram with `EffectiveImportance >= 0.7` (`storage.HighImportanceFloor`) is **never hard-deleted by the MaxEngrams (retrieval-strength) prune path**; `RetentionDays` remains an authoritative age policy, exempt from this protection — `engine.go` PruneVault, pinned by `TestPruneVault_COG20_HighImportanceExempt` (`internal/engine/engine_pruning_test.go`, RED-checked: fails with the exemption disabled). The exemption performs **no validity check**: an expired-but-important fact survives capacity pruning so `as_of` time-travel still has a destination (composes with COG-19 — invalidation is a stamp, decay/prune protection is orthogonal). Effective importance = explicit caller value (stored > 0; explicit 0 is quantized to 0.01 at write) else the memory-type table in `internal/storage/importance.go` (+0.1 when trust=verified) — the derived value is use-time only, never stored. **Scope note (increment 1):** importance drives ONLY this prune protection plus read-surface exposure — it does not touch decay rates, reinforcement, or recall scoring. Importance-modulated decay is deferred until designed against all three scoring modes (ACT-R, weighted_sum, RRF): Stability/Relevance feed the DecayFactor score component in weighted_sum/RRF, and a d_eff modulation in ACT-R lowers B(M) for fresh memories (ageDays < n+1 flips the sign of the −d·ln term) — both would silently change which results recall returns.
- **[COG-21]** A prospective notice fires ONLY when its cue entity is in the focal set of the current call — focal = entities carried by the TOP-scored returned result, or corroborated by ≥2 returned results (recall), or the caller's inline entities (remember). An armed intention's own engram (a TypeGoal engram that carries its own cue as a first-class entity) does NOT self-satisfy its own focality: its contribution to the top-result path or the ≥2-carrier corroboration count is excluded for cues it is itself armed on (`storage.IsIntentionArmedOnCue`, a 0x2D point lookup) — an intention fires only via OTHER results genuinely carrying its cue. This does not exclude TypeGoal engrams generally; a goal engram remains a legitimate corroborator of a *different* intention's cue, or of its own cue via genuinely separate carriers. Unrelated context ⇒ zero notices, always; nothing polls the armed-intention index (0x2D), there is no scheduler, and `valid_until` SILENCES an expired intention rather than firing it — `internal/engine/prospective.go`, pinned by `TestProspective_FocalGateInvariant`, `TestNoticesForRecall_SelfFocality_IntentionOwnEngramAlone`, `TestNoticesForRecall_SelfFocality_SelfCorroboration`, `TestNoticesForRecall_GenuineCorroborationStillFires` plus the acceptance harness (`prospective_harness_test.go`: precision ≥0.90, recall ≥0.80, 35 unrelated calls → exactly zero, and a Gate-4 RED arm proving the harness fails with the mechanism off). Composes with COG-11: `read_only`/observe delivery suppresses the fired-marker write (the one-shot stays armed; session dedup covers the session), pinned by `TestNoticesForRecall_ReadOnlySuppressesMarker`. The whole delivery path is opt-in (`MUNINN_PROSPECTIVE=1`); `muninn_intend` refuses cues mentioned by ≥10% of a ≥20-engram vault (the IDF arming floor — never arm a nag). *The #609 lesson made structural: no task-blind push exists to misfire. #693: self-retrieval must not fire a notice on nothing but itself.*

## Storage & durability invariants

- **[STO-1]** A new Pebble prefix must be disjoint from the keyspace registry and added to it; the disjointness cross-check must cover it. The registry lives in `internal/prefix/prefix.go`: add the prefix to `prefix.All()` and the disjointness tests (`TestAll_NoDuplicateBytes`, `TestAll_OwnerGroupsPairwiseDisjoint` in `internal/prefix/prefix_test.go`) auto-tighten to cover it — there is **no `storageMaxPrefix` constant to bump** (removed with #618's registry consolidation). — see `keyspace-registry.md`.
- **[STO-2]** Any path mutating engram **state or lease** must hold `casLocks.For(id)` across read→commit, as `CompareAndSet` (`storage/lease.go`) and `DeleteEngram` (`storage/engram.go`) do. *A new unlocked state-mutating path reopens the #594 resurrection race.*
- **[STO-3]** CAS state changes go through `UpdateMetadata` (keeps 0x0B index, caches, provenance, replication consistent) — never a direct 0x02 write — `storage/lease.go`.
- **[STO-4]** The engram lease (0x2A) is **advisory**: recall/claim paths consult it; normal writes must not start consulting it without an RFC — `storage/lease.go`, `engine/engine_lease.go`.
- **[STO-5]** `DeleteEngram` deletes association keys from **live Pebble scans**, not the engram's inline ERF list (the Hebbian worker may have moved weights), and must include the 0x2A LeaseKey in its batch — `storage/engram.go`.
- **[STO-6]** `ClearVault` ordering is load-bearing: point-delete 0x15 count → evict in-memory counter → drain coalescer → drain provenance → tombstone `DeleteRange`. Any new vault-scoped prefix MUST be added to its `dataPrefixes` list — `storage/vault_lifecycle.go`.
- **[STO-7]** MOL WAL recovery hard-fails on CRC mismatch, never skip-and-continue; replay functions must stay idempotent (last-seq is written NoSync) — `internal/wal/mol.go` `Recover`.
- **[STO-8]** HNSW: entry-point promotion happens only after the node is linked; `LoadFromPebble` validates entry-point reachability via `bfsReachable` and rebuilds if disconnected; `Registry.Insert` rolls back the orphan vector if graph insertion fails — `internal/index/hnsw/` (guards PR #471's four defects).
- **[STO-9]** Vault dimension: all insert/search paths go through `CheckDim`; a failed graph load sets `loadErr` and refuses inserts (never reports dim 0 = "empty vault" and recreates a split embedding space) — `internal/index/hnsw/registry.go` (#582/#589).
- **[STO-10]** Idempotency receipts give **no** concurrency guarantee — `WriteIdempotency`/`CheckIdempotency` are unlocked Get/Set. A caller needing exactly-once under concurrency must add its own lock. A PR claiming idempotency is race-safe is wrong.

## Security & transport invariants

- **[SEC-1]** A `cap_` token must never set `IsAPIKey` — exactly one of `IsAPIKey`/`IsCapability` is set — `internal/mcp/context.go`, `internal/mcp/types.go`. *This is what makes the recursion guard structural.*
- **[SEC-2]** Any privileged MCP tool (one that mints/grants/creates) gates on `IsAPIKey && Mode==ModeFull && <opt-in env>` before dispatch — `internal/mcp/server.go` (`muninn_create_workflow_vault` is the template). *New privileged tools must copy this triple gate.*
- **[SEC-3]** `ValidateAPIKey` accepts only the `mk_` prefix; REST/gRPC/MBP call **only** `ValidateAPIKey`, never `ValidateCapability` — `internal/auth/keys_store.go`, `middleware.go`, `grpc/server.go`, `mbp/server.go`. *Keeps cap_ MCP-only, structurally.*
- **[SEC-4]** Capabilities carry a non-nil TTL at both mint (`GenerateCapability` rejects nil) and validate (nil/past expiry = expired) — `internal/auth/capability_store.go`. *No immortal credentials.*
- **[SEC-5]** Invalid `mk_`/`cap_` on MCP fails closed — never falls through to static-token or open-server auth — `internal/mcp/context.go`.
- **[SEC-6]** Every registered MCP tool is in exactly one of `isMutatingTool`/`isReadOnlyTool`; unknown tools blocked for observe AND write modes; unknown key modes rejected — `internal/mcp/context.go`, `server.go` (enforced by `TestToolClassification_CoversAllRegisteredHandlers`). *A new tool with no classification silently escapes mode enforcement.*
- **[SEC-7]** A vault-pinned credential rejects any differing `vault` argument and never echoes the pinned name — `internal/mcp/context.go` (also REST/gRPC/MBP). *No cross-vault action, no name leak.*
- **[SEC-8]** Unconfigured vaults are locked (fail-closed, `Public:false`) on REST/gRPC/MBP — `internal/auth/vault_config.go`.
- **[SEC-9]** Toolset filtering is **advertisement-only**; dispatch never consults it; unknown values fail **open to full** — `internal/mcp/toolset.go`. *Presentation preference, not a security boundary.*
- **[SEC-10]** SSE per-POST: both a cached `cap_` and a cached `mk_` session credential are re-validated (live key-store read) before dispatch, so a revoked or expired credential cannot keep dispatching on an open SSE session — `internal/mcp/server.go`. *The cap_ half closed the #612 confused-deputy; the mk_ half closed the symmetric gap in #617 (was #615). A PR touching the SSE POST path must not reopen either.*
- **[SEC-11]** Vault names are `[a-z0-9_-]{1,64}` everywhere via `IsValidVaultName` — `internal/auth/token.go`.
- **[SEC-12]** Static-token compares are constant-time with a length cap; keys/caps are looked up by SHA-256(secret) — raw secrets are never stored — `internal/auth/token.go`, `keys_store.go`, `capability_store.go`.
- **[SEC-13]** Any new client write path in a cluster deployment must either gate on `IsLeader()`/Cortex-origin or replicate its mutation — no transport does this today, which is exactly bug #596. Background workers that mutate replicated state (e.g. the pruner) inherit the same obligation.
- **[SEC-14]** The elevated trust level `verified` (human-confirmed / admin-certified) can only be set on a write by a caller whose ctx `auth.ContextMode` is `full` or `write` — an `observe` credential is rejected with `ErrInvalidRequest`, never silently downgraded — `internal/engine/engine.go` `resolveTrust`. The gate is enforced in the engine (`Write`/`WriteBatch`), so it is transport-agnostic *only if every transport populates `ContextMode`*: REST (`internal/auth/middleware.go`), gRPC (`grpc/server.go`), MBP (`mbp/server.go` HELLO, from the key's mode / full for open sessions), and MCP (`mcp/server.go` `dispatchToolCall`, full for authorized mode-less sessions) all do. A transport that reaches `Write` without setting `ContextMode` would *over-block* (reject a legitimate full write) — that was the S8 integration bug on MBP + default-config MCP; fixed and regression-tested (`mbp/trust_mode_test.go`, `mcp/trust_write_wiring_test.go`, `engine/trust_write_test.go`). **Recorded scope decision:** "write/full credential" (D4) is deliberately the bar — so an anonymous writer to a `Public` REST vault (mapped to `ModeFull` by design) and a `cap_`/`mk_` token minted with `full`/`write` mode *can* stamp `verified`. `verified` therefore asserts "written by a full/write-authorized principal," not "cryptographically human-attested"; a stricter human-only tier would need its own mechanism and is out of scope. *Every other trust level (`inferred` default, `external`, `untrusted`) is ungated. `source_type` is provenance-derived, never a write arg, so trust is the sole caller-settable discriminator — a write path that lets an observe credential stamp `verified` makes the anti-pollution capture tiering theater (S8/D4).*
- **[SEC-15]** An `append`-mode credential (`auth.ModeAppend`) may read and CREATE new engrams (`remember`/`remember_batch`/`remember_tree`/`add_child`) but is refused every operation that modifies or deletes an EXISTING engram/entity/lease/enrichment. Enforced at the ENGINE via `Engine.refuseAppend` (returns `ErrAppendForbidden`) on ALL 30 destructive methods (data-plane + vault-admin), so the guarantee is transport-agnostic — the MCP `isAdditiveTool` dispatch gate alone left REST/gRPC/MBP open (the #687 confirmed break; Restore/Link/PruneVault were later-found stragglers). `TestAppendMode_MethodCensus` reflects EVERY exported *Engine method and fails CI on any UNCLASSIFIED one, forcing each new method into guarded/additive/infra/read-only — real completeness, not a hand-maintained checklist (principle #6, cf. SEC-6). `TestAppendMode_RefusesEveryDestructiveOp` behaviorally proves all 30 guarded ops refuse append. *One recorded residual: the additive path may reinforce an existing engram's access metadata via content-hash-dedup `TouchAccess` (#682) — append strengthens, never overwrites/evolves/forgets/archives/re-trusts. This is the structural credential the flush write reflex uses so untrusted transcript content can never turn capture into destruction (cf. SEC-7 for the cross-vault half).*

## Known open wounds

Several of these invariants sit next to known-imperfect code. The individual issues are
tracked publicly (#596, #605, #607, …); a reviewer should recognize when a PR is touching
one and either fix or at least not widen it. Cite the individual issue rather than building
a one-stop list here — a consolidated weakness map is more useful to an attacker than to a
reviewer, who is only ever looking at one diff.

Found something that isn't tracked? See [`SECURITY.md`](../../.github/SECURITY.md) — report
it privately rather than opening a public issue.
