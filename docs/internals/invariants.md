# Hard invariants

Testable assertions a PR must never violate. Anchors are on `develop`. When an anchor's
line number drifts, the symbol name is the source of truth — re-locate by grep, don't
trust the number. If the live code disagrees with an assertion here, the code wins: flag
the stale invariant, don't enforce it.

Format: **[INV-n]** assertion — `file:anchor` — *why it matters / what breaks if violated.*

## Cognition invariants

- **[COG-1]** Unknown preset name falls back to `default`, never errors — `internal/auth/plasticity.go` `ResolvePlasticity`. *Config can never wedge the engine.*
- **[COG-2]** All plasticity overrides are clamped, never rejected (HopDepth 0–8, weights 0–1, ACTRDecay 0.01–2.0, HebScale 0–50, PASMax 0–10, **AssocHalfLifeDays 0.5–3650**) — `plasticity.go`. *Out-of-range config is impossible, not merely discouraged.* For `assoc_half_life_days`, `0` means **unset** (fall through to the preset), not "clamp to the minimum" — pinned by `TestResolvePlasticity_HalfLifeClamped`.
- **[COG-3]** The `working` preset equals `default` plus exactly `{RetentionDays:7, BehaviorMode:selective}` — pinned by `TestResolvePlasticity_WorkingEqualsDefaultPlusTwoDeltas` (`plasticity_test.go`). *Editing `default` must not silently drift `working`.*
- **[COG-4]** All presets share `RecallMode="balanced"`, `ArchiveThreshold=0.05`, `InlineEnrichment="caller_preferred"`, `EnrichmentEnabled=true`, `MaxEngrams=0`, `ScoringFusion=""` — `plasticity.go` preset table + the preset-invariant test suites. *These are cross-preset guarantees other code relies on.*
- **[COG-5]** The ACT-R content gate is `contentMatch = w.SemanticSimilarity*vectorScore + w.FullTextRelevance*normalizedFTS`, where `w` is the **resolved** weights (`resolvedWeights` — from the request/plasticity, falling back to `DefaultWeights{Semantic:0.35, FullText:0.25}` only when `req.Weights == nil`) — `internal/engine/activation/engine.go` `computeACTR` + `resolveWeights`. *The content gate is weight-driven, not a fixed constant. When no weights are supplied, the 0.35/0.25 defaults apply and unused components' budget is redistributed (the `1/0.65` scale). A change to `DefaultWeights` or to the resolve/redistribute logic reshapes scoring for every request that doesn't pass explicit weights — verify against the live `resolveWeights` before asserting what the effective weights are.* **Amendment (S1):** an explicit filter defines the candidate SET; the relevance threshold only RANKS within it. Two mechanisms enforce this for candidates that matched an explicit tag filter (`inTagPool`, verified by `passesMetaFilter`), both in `internal/engine/activation/engine.go`: (1) a content-match floor (`tagMatchFloor`) in `computeACTR` gives tag-only hits a sensible positive ordering below genuine content matches; (2) a **threshold bypass** at every Phase-6 scoring cut-site (RRF, CGDN, ACT-R, and legacy weighted-sum paths) — `if final < req.Threshold && !inTagPool` — so an explicit filter match is never dropped for scoring below the relevance threshold. The floor ALONE is insufficient: a floored, content-unrelated, decayed tag hit scores ≈`0.1 * softplus(B~0.17) ≈ 0.017`, below both the ACT-R default threshold (0.1) and the MCP surface default (0.5), so without the bypass every such candidate was still silently dropped. Before this, a content-unrelated tag hit produced `contentMatch = 0` under default (ACT-R) scoring, which zeroed `final` and dropped a candidate the caller explicitly asked for via `tags_all`/`tags_any`/`tag_prefix` — breaking `due:<=today` reminders whose content is unrelated to the query. See `computeACTR`, the four cut-sites in Phase-6 scoring, and `TestComputeACTR_TagPoolFloor_*` / `TestRawTagRange_SeedsDueItems_DefaultScoring` (which asserts 12/12 due items surface at BOTH production default thresholds). The bypass is safe at every site because each is guarded by `passesMetaFilter` first — only candidates that genuinely match the filter bypass the threshold. Non-tag candidates are still thresholded normally.
- **[COG-6]** The effective default threshold is mode-aware and decided in exactly one place per path, keyed on the **effective scoring mode**, not vault config: the `activateCore` coerce runs AFTER the weights block and tests `actReq.Weights.UseRRFFusion` — for rrf-scored requests it leaves `Threshold` at `0` ("unset") so `activation.Run()` applies rrf → 0.001 (#590); otherwise `activateCore` applies the fusion-matched default via `cog6DefaultThreshold` (0.1 for ACT-R, 0.5 for weighted_sum since #754). Keying on the effective scoring mode (rather than `resolved.ScoringFusion`) keeps the threshold default consistent with the scoring math that actually runs even when a caller passes explicit weights on an rrf vault (vault config says rrf, but caller-weights requests score ACT-R and must get the 0.1 default) — `internal/engine/engine.go` `activateCore`, `internal/engine/activation/engine.go` `Run`, `internal/mcp/handlers.go` `handleRecall`. An explicit caller threshold is never modified at any layer. Pinned at the **engine** layer (not `Run()`) by `TestActivate_RRFDefaultThreshold_EndToEnd` (`internal/engine/engine_rrf_threshold_test.go`) plus its ACT-R control `TestActivate_ACTRDefaultThreshold_Unaffected`. *R1 (#590 follow-up): before this, `activateCore` unconditionally coerced `Threshold==0 → 0.1` BEFORE `activation.Run()` ever saw the request, making #590's mode-aware default (rrf → 0.001) dead code on every production transport (MCP, REST, gRPC, MBP, embedded) — RRF vaults returned silently-empty default recall. The pre-existing `Run()`-level regression test (`TestRRF_ReturnsResultsWithDefaultThreshold`) stayed green throughout because it calls `Run()` directly with `Threshold: 0`, a call shape production never produces — exactly why the new pin lives at the engine layer instead.* MCP additionally: when the `threshold` arg is omitted, `handleRecall` consults the vault's `ScoringFusion` and passes `0` through (not its historical flat `0.5` prefill) for rrf vaults — and likewise passes `0` whenever a recall `mode` is present, because the mode's preset replaces the 0.5 default and resolving it is the engine's decision; an explicit caller-supplied threshold at or above 0.01 against an rrf vault that returns zero results gets a loud hint (never a silent, unexplained empty), not a clobbered value. **Amendment (#704):** recall-mode presets were a SECOND threshold decider that bypassed the mode-aware default — transports stamped ACT-R-calibrated preset thresholds (semantic 0.3, recent 0.2, deep 0.1) into the request, and the engine's vault-default `recall_mode` block overrode the leave-0-for-rrf decision, so a mode-carrying recall on an rrf vault was still silently empty. Now the ENGINE is the single preset decider: transports (MCP `handleRecall`, REST `handleActivate`) validate the mode name and forward it on the wire (`ActivateRequest.Mode` — previously silently dropped for raw MBP/embedded callers, now honored; gRPC's proto carries no mode field, so that surface is unchanged, and an invalid mode from a raw wire caller is silently ignored — fail-open on presentation, matching the engine's total-ignore of the wire field before; transports rejected invalid modes then and now). The engine resolves the preset in `recall_mode_preset.go` + the weights block, where the effective scoring mode is known: under rrf fusion the preset threshold ABSTAINS (Threshold stays 0 → `Run()`'s rrf floor); preset hops apply unless the caller set `MaxHops` or explicitly `DisableHops`. Preset WEIGHTS have three deliberate cases: (1) explicit weight-carrying mode (`semantic`/`recent`) with no caller weights → the preset defines the FULL weight vector from the ZERO base — the exact struct transports used to stamp — because the preset zero-value scheme cannot express semantic's implicit "decay/hebbian/access/recency = 0", and overlaying resolved defaults lets a fresh, recently-active engram score ~0.7 under legacy scoring with zero content match, above semantic's own 0.3 threshold (silently-wrong-results class, caught in this increment's refute); (2) caller weights present (any mode source) → preset fills only wire-zero fields, caller-set fields always win; (3) vault-default mode with no caller weights → the vault's resolved weights stand and only the `DisableACTR` strategy bit applies (a background default tints, it does not respecify scoring — byte-preserving develop's effective behavior on that path, where resolved-side zero-guards made the scalar fill a no-op). Presets never change the FUSION mode (`UseRRFFusion` comes from vault config or genuinely caller-explicit weights — previously, a weight-carrying preset stamped client-side silently flipped an rrf vault to weighted-sum scoring); on non-rrf vaults an explicit weight-carrying mode does select its scoring STRATEGY (the zero-base vector carries the preset's `DisableACTR` bit), exactly as its stamped form always did. `balanced` means engine defaults: the engine skips it, and MCP keeps its historical 0.5 surface default for it. Pinned by `TestActivate_RRFVaultDefaultRecallMode_NotSilentlyEmpty` (RED without the abstention), `TestActivate_RRFExplicitWireMode_ThresholdAbstains`, `TestActivate_ACTRVaultDefaultRecallMode_PresetThresholdUnchanged` + `TestActivate_ACTRExplicitWireMode_AppliesPreset` (ACT-R paths unmoved / wire mode honored), and the transport wire pins `TestHandleRecallModeForwardedNotStamped` (MCP, RED before: `Mode==""`, `Threshold==0.1`) and `TestActivate_ModeForwardedNotStamped` (REST).

- **[COG-22]** Post-pipeline injection is gated and supersession substitutes atomically under the caller's view. The gate is two-layered on purpose: `Nameable` (state, meta filters, trust, structured filter, lease) governs whether an ID may surface anywhere the SUPERSESSION RANKING PHASE emits — result rows and its always-on `SupersededBy`/`CurrentVersion` annotations alike — for these predicates the ID itself is the secret (#548); `ValidForView` (COG-19) governs only what may be presented as CURRENT, because supersession stamps every superseded engram and expired chain intermediates are legitimate, nameable lineage. Supersession resolves its head by walking chains through hidden nodes without ever naming them (deepest nameable node valid for the view wins; under `as_of`, nodes postdating the instant may not even be named), and a chain with no such node abstains WHOLE — no injection, no demotion, no `SupersededBy`/`CurrentVersion` annotation. Half-applied substitution is the forbidden state: demote-without-inject silently truncates the topic, and an annotation naming a hidden node is the #548 leak in metadata form. Pinned by the guard tests in `engine_supersession_test.go` — the per-predicate guards each RED-checked against their bypassed check, `ViewFuture` pinned by its own backdated-successor test — and `TestEntityBoost_InjectionRespectsStructuredFilter`. *An injector that sees less than the pipeline re-opens phase-6 holes one field at a time (#654, the #570 rounds, the structured filter — three review cycles, same class); the gate exists so the next visibility field lands in exactly one place.* **Amendment (COG-27, #763):** a declared-supersession predecessor may be NAMED as substitution provenance under `visibilityGate.NameableAsLineage` — `Nameable` with the lifecycle predicate evaluated as `PassesLifecycle(eng, asOf, includeInvalid=true)`, which admits a soft-deleted record ONLY when it carries a closed `ValidUntil` (still refusing `StateArchived` and open-stamp forget trash). It is a separate method, never a loosening of `Nameable`, so the bad state stays unrepresentable for every other injector (principle #3). Pinned by `TestVersionHead_PredecessorWordingReturnsHead` (RED-checked: swapping `NameableAsLineage` for `Nameable` makes it fail) and `TestVersionHead_PredecessorUnderForeignLeaseIsNotEvenAShadow`.

- **[COG-29]** **When two results in a recall response are joined by an UNRESOLVED DECLARED `contradicts` edge, recall must not present either as the answer.** Both are returned, DEMOTED below the score they earned, in a defensible order, with a first-class per-row annotation, and the response carries a `conflict` block naming the pair and the resolution actions. The phase (`internal/engine/engine_contradiction.go` `applyContradictionHonesty`, issue #764) is **DEMOTE-ONLY** — every score change is a `min()` against the row's own earned score, so a conflict can only ever push a row DOWN, never above a genuinely better unrelated match — **never removes a row** (`len(out) == len(in)`), **never abstains**, and **WRITES NOTHING** (observe-safe by construction, COG-11).

  **"Declared" means an explicit `storage.RelContradicts` edge on a 0x03/0x04 key, and nothing else.** No similarity-inferred conflict, ever — the same asserted/inferred boundary #758/#763 established and COG-25 restates. Deliberately keyed on the EDGES rather than the 0x0A marker: that marker's key is `…|id(16)` with a single-partner value, so one engram can record exactly one partner and a second contradiction overwrites the first (keyspace-registry 0x0A).

  **Unresolved** means all of: (1) the edge is declared; (2) BOTH endpoints are live — not soft-deleted, not archived, validity window not elapsed, and nameable under the caller's visibility gate; (3) no `RelSupersedes` exists between the pair in either direction ("I declared which one wins" IS a resolution — asserted beats asserted, COG-25's doctrine); (4) under `as_of`, the edge existed at the caller's instant (a zero `CreatedAt` is a legacy edge, treated as always-existing — never invent a time, and over-warn beats under-warn on a correctness signal). Clause 3 is isolated by `TestContradictionHonesty_SupersedesEdgeAloneResolves`, which writes the `RelSupersedes` edge STRAIGHT THROUGH THE STORE: the engine's `Link(supersedes)` also retires the target, so a test that goes through `Link` is cleared by clause 2 and passes with clause 3 deleted — it proves nothing about clause 3. Clause 2's rule is applied by both recall (`contradictionEndpointLive`) and the report (`markResolvedContradictions`, which currently inlines an equivalent retirement closure — same rule, two sites; collapsing them into the shared function is cheap hygiene whenever either is next touched), so recall and the report agree on whether a conflict is live. **It is the clause that makes resolution work at all**: before #764 NO operation in the product cleared a declared contradiction — evolve, forget (soft), forget(not_true_since), hard-delete and `muninn_decide` all left both the edge and the marker in place, so an agent that resolved a conflict the way the tool advises watched the theater continue forever, with a hard-deleted endpoint rendering a permanently blank-concept row. Note that "in the result set" is NOT proof of liveness: under `include_invalid` a retired endpoint is returned, and treating its presence as liveness keeps the theater running past the resolution.

  **Not top-level abstention**, which is what one round-7 evaluator literally asked for. #747/#754 is the hard-learned lesson in this exact area: suppressing BOTH sides destroys the true memory exactly as hard as the false one, and the agent that did the right thing loses both facts and the conflict itself. It also breaks the `Abstained` wire contract ("Empty iff Abstained is false") that two admission-worthy candidates do not satisfy. The complaint underneath the ask — "an agent commonly consumes only the first result, so this is confidently misleading" — is about presenting one side as THE ANSWER, not about returning the data; the demote, the always-on per-row annotation and the `conflict` block remove "the answer" while keeping both facts.

  **Named deviations from the design, each with its reason.** (a) **Ordering is by score, and only by score.** After the demote the whole response is RE-SORTED by score with a stable sort; adjacency is whatever that produces. Neither gather direction is used. The design asked for gather-to-highest, which would lift a cluster member above a strictly better unrelated row — exactly what demote-only forbids. The first implementation therefore gathered to the cluster's LOWEST-ranked member instead, and that is worse: on a corpus with a dominant conflicted row (0.859) whose declared partner is a weak straggler (0.018), it moved the best answer from rank 0 to rank 6, behind five rows it outscores by 2-8x, and returned a response that was no longer score-descending — an agent reading the first result then gets a 0.5 row presented as the answer over a 0.77 row, a worse lie than the one the phase exists to fix. Sorting by the demoted score is both demote-only AND monotone: near-tied rivals (the evaluators' shape) land adjacent for free, a dominant answer stays at rank 0 demoted and annotated, and nothing is ever lifted because a row's score only ever went down. The intra-cluster ladder (`sortContradictionCluster`) is applied first as a permutation within the cluster's own positions, so it decides sibling order on an exact score tie and nothing else. `keepAtLeast`/`adjacency_overflow` are computed from POST-SORT positions — the demote itself can push a member below rows that used to score under it, so computing against pre-sort ranks silently cuts a conflict in half while reporting that it did not (pinned by `TestContradictionHonesty_DominantAnswerStaysRankZero` and `TestContradictionHonesty_AdjacencyOverflowUsesPostSortRanks`). (b) The design's "if any cluster member survives the MaxResults cut, all of them do" does not hold at a tight limit: phase 6 truncates to `MaxResults` inside `activation.Run` BEFORE any post-pipeline phase, so a partner beyond the limit never reaches this phase, and injecting it is deferred (neither side is known to be right, so a conflict must never LIFT content into a result set it did not earn). What holds instead, and is pinned, is that the surviving row is still demoted and annotated with the partner named and `partner_in_results: false` — an agent consuming only the first result is still told it is disputed. The `keepAtLeast`/`adjacency_overflow` machinery still defends the case where a post-pipeline injector grows the set past `MaxResults`.

  **No absolute score ceiling.** An earlier draft carried a hard 0.95 cap and a `score_capped` wire field. Recall's `Score` is an absolute activation that is structurally an order of magnitude below that on every corpus measured, so the ceiling never once bound: it shipped a permanently-false flag on four surfaces and a test assertion that could not fail. Both were removed. The honest statement of the guarantee is the relative one — `contradictionDemote` (10%), a single `min()` against the row's own earned score.

  **The per-row annotation names exactly ONE partner, and the choice is total.** A row can be an endpoint of several declared edges; selection prefers a partner that is itself in the result set, then the lowest partner ULID. Taking the first edge encountered while ranging the map `GetAssociations` returns made both `with` and `partner_in_results` flip between identical queries against an unchanged vault (measured: a 33/7 split over 40 calls). Pinned by `TestContradictionHonesty_PartnerChoiceIsDeterministic`.

  **Fast path — three probes, cheapest first.** (1) A per-vault in-process flag set by `Engine.Link`, so a single-binary deployment honors a declaration on the very next query. (2) A bounded 0x0A seek (`PebbleStore.HasContradictionMarkers`, one iterator `First()`), the steady state and the only probe that sees an edge declared by ANOTHER process. (3) Once per vault per process, `DeclaredContradictions` — a bounded forward-association scan for declared-but-unflagged edges, its verdict memoised per vault.

  Probe 3 exists because 1 and 2 together had a PERMANENT hole. The in-process flag lives only in memory and the 0x0A marker is written only when the batch worker flushes, so a process that restarts between `muninn_link(contradicts)` and that flush loses the flag while the marker was never written — and nothing re-probed. Recall then silently stopped honoring a durable, correctly-declared contradiction FOREVER, which is the project's worst failure class dressed as a fast path. Pinned by `TestContradictionHonesty_SurvivesRestartBeforeTheMarkerFlush` (declare, assert no marker, clear the in-process state, recall must still honor) and `TestContradictionHonesty_ProbeIsPaidOncePerVault` (the memoisation, so recall never pays the scan twice). A probe ERROR — marker or declared-edge — degrades toward doing the work, never toward silently disabling the phase, and so does an incomplete scan (a vault with more forward associations than `DefaultDeclaredContradictionScanCap`).

  **Named residual:** an edge declared by another process/node AFTER this process memoised a clean verdict is honored only once its 0x0A marker lands (≤ one worker interval after the COG-23 #764 amendment) — probe 2 still runs on every query, so nothing regressed here.

  **`contradictionsDeclared` is never evicted, deliberately.** Eviction would have to prove no unresolved declared contradiction remains anywhere in the vault — a vault-wide scan, the exact cost this gate avoids — and getting it wrong turns honesty off silently. The entry is an empty struct keyed by an 8-byte prefix; the retained set is bounded by vault count. The false positive costs a read-only bounded phase that returns no block when nothing is live.

  Because the corpora contain no `contradicts` edge, the phase is a provable no-op on all three (`TestContradictionHonesty_NoContradictionsIsANoOp`), which is what keeps their numbers byte-identical. **Measured cost** (`BenchmarkRecallContradictionGate`, 200-engram synthetic vault, 1000 recalls x3): gate closed p50 348-383us / p99 1.03-1.32ms; gate OPEN p50 360-372us / p99 1.03-1.22ms — the open gate is inside the noise of the closed one. The once-per-process declared-edge scan is 8.5ms over 100k associations (`BenchmarkDeclaredContradictions`).

  Surface scope: MCP + MBP + REST (alias). gRPC and the non-Go SDKs carry NO annotation fields at all, so adding only this one would be the silently-wrong class — obligation #3, a deliberate omission. Pinned by `internal/engine/engine_contradiction_honesty_test.go`, `..._resolution_test.go` (every resolution path, RED-checked at `bb10f30`) and `internal/mcp/contradiction_honesty_test.go` (the two places an MCP field silently vanishes). **Accepted residual:** an agent that declares a conflict and walks away leaves both facts demoted 10% — visible, recoverable via three named actions the warning spells out, and strictly better than one of them being presented as the truth.

- **[COG-30]** **Every recall row carries an ABSOLUTE `relevance_band` (a WORD, never a float), and the phase that assigns it is a PURE ANNOTATION** (#773, `internal/engine/engine_relevance.go` `applyRelevanceBands` + `internal/engine/activation/relevance.go`). Pinned by `TestPrefixUpperBound_IsTightAndNeverCrossesIntoANeighbouringPrefix` (`internal/storage/keys/scan_test.go`), whose load-bearing half is "no key from a DIFFERENT prefix is admitted".

- **[STO-12]** **An association edge is refused unless BOTH of its endpoints have a live 0x01 engram record** — `internal/storage/assoc_endpoints.go` — the 0x03 forward key, the 0x04 reverse key, the 0x14 weight index and the 0x25 archive row all inherit this (#803).

  *A refusal at every writer, NOT an unrepresentable state, and the wording is deliberate.* The first version of this entry claimed an edge "may only exist while" both endpoints are live, which asserts the principle-#3 structural impossibility that the mechanism does not deliver. `engramExists` reads through `ps.db.Get` and the write commits a separate batch, with nothing spanning the two — `DeleteEngram` holds `casLocks.For(id)` across its read→commit (STO-2), the association writers take no lock — so a hard delete that lands inside the check→commit window still leaves a row. **Measured residual: 6 dangling rows per 400 forced `DeleteEngram`-vs-`WriteAssociation` races (pre-guard: 400/400).** Closing it structurally was considered and rejected: `casLocks` on both endpoints would work for `WriteAssociation` alone, but `pebbleStoreBatch` holds an open batch across arbitrary CALLER code between its check and its commit, so no lock discipline the store can enforce covers it — the claim would still have to be qualified, at the price of N-lock ordering against a single-lock `DeleteEngram`. The residual is a repairable row and it belongs to the deferred O(vault) integrity/repair pass, not to a lock.

  *Liveness is EXISTENCE, not lifecycle state.* `SoftDelete` `batch.Set`s the 0x01 key with `StateSoftDeleted`, and archiving is a state on a present record, so a soft-deleted or archived engram **is present** and its edges must survive — a state-aware predicate here would silently destroy every restorable engram's edges, which is worse than the leak it closes (pinned by `TestSTO12_SoftDeletedAndArchivedEndpointsKeepTheirEdges`). Only `DeleteEngram` removes 0x01.

  **Two layers, both required.**

  *(1) The cascades.* `DeleteEngram` cascades 0x25 in both directions (it scanned 0x03/0x04 only), and every hard-delete CALLER must clean the FTS and HNSW indexes, which live outside the store — `Engine.Forget(hard)` and **both** `Engine.PruneVault` arms (MaxEngrams and RetentionDays are separate delete loops with separate call sites) do so via `cleanSearchIndexesAfterHardDelete`. The 0x03/0x04 cascade scans must also obey **STO-11**: a 0x03 key is `prefix(25)|weightComplement(4)|dst(16)` and `keys.WeightComplement` is `MaxUint32 - uint32(w*MaxUint32)`, so `complement[0] == 0xFF` for every weight at or below ~1/256 and the complement is `0xFFFFFFFF` at weight 0 — which is byte-for-byte the position every PRE-FIX weight-1.0 edge was written at (`legacyFullWeightComplement`). The original naive `append(prefix, 0xFF)` bound sorted at or below all of those, so the cascade silently skipped them and nothing else ever reaped them. **Client-reachable at ordinary weights** (nothing clamps `Weight` on `Engine.Link` or the inline path), and it made `RepairLegacyFullWeightAssocKeys` a *creator*: that pass scans with a correct bound, so it saw the stranded legacy row the cascade missed and relocated it into a live, correctly-positioned dangling edge at startup. Both bounds now use `keys.PrefixUpperBound`, and the repair's `flushChunk` live re-validation additionally requires both endpoints — needed independently, because the vaults that pass exists for were hard-deleted by a pre-fix binary whose cascade could not reach the legacy position either. Note the other direction too: `keys.PrefixUpperBound` WAS LOOSE — it incremented the first sub-0xFF byte from the right and returned WITHOUT clearing the trailing 0xFF bytes, so for a 25-byte assoc prefix ending in 0xFF the bound spanned into the neighbouring engram's association keyspace; `storage.PrefixIterator` open-coded the identical loop. **#816 fixed both** (the helper carries and truncates; `PrefixIterator` delegates to it). **Every destructive scan bounded by a 25-byte `kind|ws(8)|id(16)` prefix nevertheless KEEPS its explicit `bytes.Equal(k[:25], prefix)` break** — belt and braces now rather than the sole protection, because a delete loop should not depend on a helper in another package for the only thing holding it inside its own keyspace, and because any future non-ULID id tail collapses the ~2^-64 gap below to zero. There are four of them: `DeleteEngram`'s 0x03 forward and 0x04 reverse cascades, `DeleteEngram`'s 0x25 archived-source cascade, and `reapArchivedEdgesFrom` (reachable from the recall read path via `RestoreArchivedEdges`). The 0x03/0x04 pair must additionally keep `SeekGE` rather than being converted to `PrefixIterator` (whose First/Valid shape changes the break-vs-continue semantics on short keys). **There is a FIFTH scan over the identical 25-byte `0x25|ws|src` prefix that has NO such break, so its upper bound is its ONLY protection**: `RestoreArchivedEdges`' own candidate loop, twenty lines above `reapArchivedEdgesFrom` in the same file. It hand-rolls its own TIGHT upper bound (incrementing from the right and zeroing every byte it wraps) instead of calling `PrefixUpperBound` or `PrefixIterator`, which is why it was correct while those were loose. #816 makes the shared helper agree with it, and **the loop still stays hand-rolled**: "equivalent today" plus "the only thing standing between this loop and fabricated edges" is not a combination to maintain at a distance. Dropping that bound — by consolidating onto the shared helper and then regressing it, or by "tidying" this loop for consistency with its neighbour — would make it FABRICATE a `victim → neighbour's dst` edge that never existed and stamp `restoredAt` on it, permanently exempting it from `GCArchivedEdges`; this loop is destructive AND creative, unlike the four above. Its `engramExists(ws, c.dst)` guard does not catch that: the dst read out of the neighbour's key is a real live engram, so liveness and the bound are orthogonal. The bound is pinned by `TestSTO11_RestoreArchivedEdgesCandidateScanStaysInsideItsOwnPrefix`; a prefix check must not be folded into that loop's existing `len(k) < 41 || len(v) < 26` skip, because `len(v) < 26` is value-shaped and must stay a `continue` while a prefix mismatch must `break`.

  *Read the ~1-in-256 number correctly.* It is the rate at which the BOUND IS LOOSE, not the rate at which anything is lost — the two differ by about 64 bits. To land inside the widened band a second engram must share the victim's first 14 ID bytes: the entire 48-bit ULID millisecond timestamp AND 8 of the 10 crypto-random entropy bytes, i.e. ~2⁻⁶⁴ *on top of* a same-millisecond collision. With ULID-shaped keys that is **not operationally reachable**, and every test of it constructs its IDs by hand. The guard is therefore **structural hygiene, not a live data-loss fix**: a mandated shared helper whose contract is wrong, compensated by an explicit per-key check at each call site, where any future non-ULID ID tail (a counter, a truncated hash, a content-addressed key) collapses the 64-bit gap to zero immediately — silently, on a delete path. Pinned by `TestSTO11_EveryDestructivePrefixScanStaysInsideItsOwnPrefix` (the table over all four scans; grow it when a fifth appears), `TestSTO12_DeleteEngramCascadeReachesEveryWeightPosition`, `TestSTO12_DeleteEngramCascadeStaysInsideItsOwnPrefix`, `TestSTO12_LegacyFullWeightRepairNeverCreatesADanglingEdge` and `TestSTO12_HardDeletePathsCleanTheSearchIndexes`.

  *(2) The guard.* **Enumerate the writer set from the KEY BUILDERS, never from method names or from prose** — `grep -e AssocFwdKey -e AssocRevKey -e AssocWeightIndexKey -e ArchiveAssocKey` over non-test Go. The first version of this entry enumerated by name, claimed four writers, and missed four more with no "Association" in their signature at all: the inline-`Associations` loops in `PebbleStore.WriteEngram`, `PebbleStore.WriteEngramBatch` and `pebbleStoreBatch.WriteEngram`, plus the singular `UpdateAssocWeight`. **Those three inline loops are client-reachable** — `mbp.WriteRequest.Associations` arrives from REST (`rest.WriteRequest` is a type alias), gRPC, MBP and the embedded library, so an ordinary client holding an ID across a delete landed three dangling rows with a nil error; only MCP escaped, because `muninn_link`/`muninn_remember` use `relationships`, which routes through the guarded primitive. The full creator set, all refusing with `ErrDanglingEndpoint`, is: `WriteAssociation` (the primitive, through which `autoassoc.processJob`, `NeighborWorker`, `GoalLinkWorker`, the refines writer, `plugin/store_adapter.go` and inline caller *relationships* reach the keyspace), `pebbleStoreBatch.WriteAssociation`, `UpdateAssocWeight`, `UpdateAssocWeightBatch`, `RestoreArchivedEdges`, and the three inline-`Associations` engram writers. Non-creators the same grep returns, and why they are exempt, are recorded at the head of `assoc_endpoints_writers_test.go`. Guarding one amplifier site would be cosmetic: the next worker added would reintroduce the class. Pinned by `TestSTO12_EveryAssociationCreatorRefusesDeadEndpoints` (the enumerated table; grow it when the grep grows) and `TestSTO12_InlineAssociationsCannotNameADeadEngram` (the surface-reachable arm, asserted against the same census as the delete paths).

  *The engram writers check the TARGET only.* The engram carrying the associations is their source and its own 0x01 key is Set in the same uncommitted batch, so a both-endpoints DB read would reject every engram that has ever carried an inline association. `WriteEngramBatch` additionally treats any caller-supplied id elsewhere in the same call as live, ORDER-INDEPENDENTLY, because it sees the whole slice up front — but that promise is only sound if the sibling actually commits: the per-item validations that run afterwards (encode, the up-front raw-tag validation, STO-12 itself) each `continue` without queueing that item's 0x01, so the referrer's edges to a refused sibling are `batch.Delete`d after the loop. **Not fixed by accumulating the sibling set incrementally** — that reintroduces the queue-order dependence `TestSTO12_BatchAssociationGuardIsQueueOrderDependent` documents for `pebbleStoreBatch` and refuses the legitimate referrer-first ordering. **The predicate for that post-loop delete is `engramExists` PLUS the set of ids that another item in the same call commits, never the batch outcome.** Two distinct ways a refused item is still a live endpoint, and the delete must survive both: (a) a refused *update* leaves its 0x01 record in place, which `engramExists` sees; (b) the SAME id appears twice in one call, once committing and once refused, which `engramExists` CANNOT see — the successful occurrence's 0x01 `Set` is still in the uncommitted batch, so a DB read returns false and the referrer's edges to an endpoint that is about to commit are deleted in the same batch, after the `Set` that made it live. Hence the `committedIDs` set alongside the existence check. In both cases deleting is unrecoverable loss, where the hole being closed only leaks a repairable dangling row. Note also that two later `continue`s in the same loop (`WriteRawTagIndexEntry`, the 0x22 last-access `batch.Set`) fire *after* the item's 0x01 and association Sets are queued; both are unreachable today (the first re-runs the identical validation, the second fails only past a 4 GB batch), but a validation moved below the queueing would invert the repair. Pinned by `TestSTO12_BatchSiblingThatFailsItsOwnValidationIsNotALiveEndpoint`. **`pebbleStoreBatch` must additionally treat an engram queued EARLIER IN THE SAME BATCH as live** — `RememberChild` and `Evolve` queue the engram and its edge into one uncommitted batch, so a DB-read-only guard would reject every atomic child-append and every evolve.

  **The guard FAILS OPEN on a read fault — but counts and logs it** (`GuardReadFaults`, plus a WARN rate-limited to one per 30 s because a corrupt block is a permanent key-scoped fault). Fail-open is right and is *not* in tension with #809: #809 refuses on a read failure because proceeding would fabricate metadata over live data; this permits because refusing would destroy a live edge that can never be recovered — opposite loss directions, one doctrine. A silent fail-open would not be: it reverts the whole invariant to pre-#803 behaviour with nothing in the logs.

  *Ancillary obligations.* `DeleteEngram` also drops the 2 s-TTL `assocCache` entry of every source that pointed at the victim: the ROWS all go, but the SERVED graph kept naming the dead engram until expiry. `RestoreArchivedEdges` REAPS an unrestorable 0x25 prefix rather than restoring it: a restore stamps `restoredAt`, and `GCArchivedEdges` requires `restoredAt == 0`, so a restored-then-re-archived dangling edge would be permanently GC-exempt (`reapArchivedEdgesFrom`, pinned by `TestSTO12_ArchivedEdgesFromAHardDeletedSourceAreReaped`). Cost of the guard is one Pebble point read per endpoint, measured at 0.55–1.1 µs and independent of engram size (+1.0–1.6 µs on a 2.9 µs primitive; `assoc_endpoints_bench_test.go`). Behaviourally pinned end-to-end by `TestSTO12_NoDanglingAssociationEdges` (`internal/engine/engine_dangling_edges_test.go`), a table over the real delete/restore/repair sequences.

  *Three non-obvious facts measured rather than assumed:* `UpdateAssocWeightBatch` **does** create edges from nothing (#809 made a read FAILURE skip the pair, but read ABSENCE is a normal fact returning a nil error and a zero tuple, so a pair naming two engram-less ULIDs falls through both reads and Sets a fresh row, returning nil); `DecayAssocWeights` never reads 0x01, so nothing in the system ever reaped any of this — 24 passes with real `default` preset parameters deleted zero; and a client can steer an edge into the 0xFF complement band with nothing more exotic than `weight: 0.001`.

## Security & transport invariants

- **[SEC-1]** A `cap_` token must never set `IsAPIKey` — exactly one of `IsAPIKey`/`IsCapability` is set — `internal/mcp/context.go`, `internal/mcp/types.go`. *This is what makes the recursion guard structural.*
- **[SEC-2]** Any privileged MCP tool (one that mints/grants/creates) gates on `IsAPIKey && Mode==ModeFull && <opt-in env>` before dispatch — `internal/mcp/server.go` (`muninn_create_workflow_vault` is the template). *New privileged tools must copy this triple gate.*
- **[SEC-3]** `ValidateAPIKey` accepts only the `mk_` prefix; REST/gRPC/MBP call **only** `ValidateAPIKey`, never `ValidateCapability` — `internal/auth/keys_store.go`, `middleware.go`, `grpc/server.go`, `mbp/server.go`. *Keeps cap_ MCP-only, structurally.*
- **[SEC-4]** Capabilities carry a non-nil TTL at both mint (`GenerateCapability` rejects nil) and validate (nil/past expiry = expired) — `internal/auth/capability_store.go`. *No immortal credentials.*
- **[SEC-5]** Invalid `mk_`/`cap_` on MCP fails closed — never falls through to static-token or open-server auth — `internal/mcp/context.go`.
- **[SEC-6]** Every registered MCP tool is in exactly one of `isMutatingTool`/`isReadOnlyTool`; unknown tools blocked for observe AND write modes; unknown key modes rejected — `internal/mcp/context.go`, `server.go` (enforced by `TestToolClassification_CoversAllRegisteredHandlers`). *A new tool with no classification silently escapes mode enforcement.*
- **[SEC-7]** A vault-pinned credential rejects any differing `vault` argument and never echoes the pinned name — `internal/mcp/context.go` (also REST/gRPC/MBP). *No cross-vault action, no name leak.*
- **[SEC-8]** Unconfigured vaults are locked (fail-closed, `Public:false`) on REST/gRPC/MBP — `internal/auth/vault_config.go`.
- **[SEC-9]** Toolset filtering is **advertisement-only**; dispatch never consults it; unknown values fail **open to full** — `internal/mcp/toolset.go`. *Presentation preference, not a security boundary.*
- **[SEC-10]** SSE per-POST: both a cached `cap_` and a cached `mk_` session credential are re-validated (live key-store read) before dispatch, so a revoked or expired credential cannot keep dispatching on an open SSE session — `internal/mcp/server.go`. *The cap_ half closed the #612 confused-deputy; the mk_ half closed the symmetric gap in #617 (was #615). A PR touching the SSE POST path must not reopen either.*
- **[SEC-11]** Vault names are `[a-z0-9_-]{1,64}` everywhere via `IsValidVaultName` — `internal/auth/token.go`.
- **[SEC-12]** Static-token compares are constant-time with a length cap; keys/caps are looked up by SHA-256(secret) — raw secrets are never stored — `internal/auth/token.go`, `keys_store.go`, `capability_store.go`.
- **[SEC-13]** Any new client write path in a cluster deployment must either gate on `IsLeader()`/Cortex-origin or replicate its mutation — no transport does this today, which is exactly bug #596. Background workers that mutate replicated state (e.g. the pruner) inherit the same obligation.
- **[SEC-14]** The elevated trust level `verified` (human-confirmed / admin-certified) can only be set on a write by a caller whose ctx `auth.ContextMode` is `full` or `write` — an `observe` credential is rejected with `ErrInvalidRequest`, never silently downgraded — `internal/engine/engine.go` `resolveTrust`. The gate is enforced in the engine (`Write`/`WriteBatch`), so it is transport-agnostic *only if every transport populates `ContextMode`*: REST (`internal/auth/middleware.go`), gRPC (`grpc/server.go`), MBP (`mbp/server.go` HELLO, from the key's mode / full for open sessions), and MCP (`mcp/server.go` `dispatchToolCall`, full for authorized mode-less sessions) all do. A transport that reaches `Write` without setting `ContextMode` would *over-block* (reject a legitimate full write) — that was the S8 integration bug on MBP + default-config MCP; fixed and regression-tested (`mbp/trust_mode_test.go`, `mcp/trust_write_wiring_test.go`, `engine/trust_write_test.go`). **Recorded scope decision:** "write/full credential" (D4) is deliberately the bar — so an anonymous writer to a `Public` REST vault (mapped to `ModeFull` by design) and a `cap_`/`mk_` token minted with `full`/`write` mode *can* stamp `verified`. `verified` therefore asserts "written by a full/write-authorized principal," not "cryptographically human-attested"; a stricter human-only tier would need its own mechanism and is out of scope. *Every other trust level (`inferred` default, `external`, `untrusted`) is ungated. `source_type` is provenance-derived, never a write arg, so trust is the sole caller-settable discriminator — a write path that lets an observe credential stamp `verified` makes the anti-pollution capture tiering theater (S8/D4).*
- **[SEC-15]** An `append`-mode credential (`auth.ModeAppend`) may read and CREATE new engrams (`remember`/`remember_batch`/`remember_tree`/`add_child`) but is refused every operation that modifies or deletes an EXISTING engram/entity/lease/enrichment. Enforced at the ENGINE via `Engine.refuseAppend` (returns `ErrAppendForbidden`) on ALL 30 destructive methods (data-plane + vault-admin), so the guarantee is transport-agnostic — the MCP `isAdditiveTool` dispatch gate alone left REST/gRPC/MBP open (the #687 confirmed break; Restore/Link/PruneVault were later-found stragglers). `TestAppendMode_MethodCensus` reflects EVERY exported *Engine method and fails CI on any UNCLASSIFIED one, forcing each new method into guarded/additive/infra/read-only — real completeness, not a hand-maintained checklist (principle #6, cf. SEC-6). `TestAppendMode_RefusesEveryDestructiveOp` behaviorally proves all 30 guarded ops refuse append. *One recorded residual: the additive path may reinforce an existing engram's access metadata via content-hash-dedup `TouchAccess` (#682) — append strengthens, never overwrites/evolves/forgets/archives/re-trusts. This is the structural credential the flush write reflex uses so untrusted transcript content can never turn capture into destruction (cf. SEC-7 for the cross-vault half).*
